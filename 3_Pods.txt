Практика 3. Поды (Pods).

Готовые манифесты к этой практике лежат в manifests/03_pods/ — их можно
применять напрямую, не набирая YAML руками.

ЗАМЕНА ПЕРЕД НАЧАЛОМ: в манифестах части 1 замените YOUR_DOCKERHUB_LOGIN
на ваш логин на Docker Hub, иначе поды уйдут в ImagePullBackOff.
Манифесты части 2 используют готовые публичные образы и замены не требуют.


=========================================================================
ЧТО ТАКОЕ ПОД И ЗАЧЕМ ОН НУЖЕН
=========================================================================

Под — минимальная единица развёртывания в Kubernetes. Это не контейнер:
под — это обёртка вокруг одного или нескольких контейнеров, которые
всегда запускаются вместе на одной ноде.

Что даёт эта обёртка, то есть зачем вообще понадобился ещё один уровень:

  * ОБЩИЙ СЕТЕВОЙ АДРЕС. У всех контейнеров пода один IP и один сетевой
    namespace. Они видят друг друга по localhost и не могут занять один
    и тот же порт. В обычном Docker для этого нужно было бы связывать
    контейнеры через сеть вручную.
  * ОБЩИЕ ТОМА. Контейнеры пода монтируют одни и те же тома и могут
    обмениваться через них файлами.
  * ОБЩАЯ СУДЬБА. Под планируется на ноду целиком, переезжает и удаляется
    целиком. Контейнеры внутри всегда вместе.

Второй контейнер в поде — не «плохая практика» сама по себе. Так делают
вспомогательные контейнеры (sidecar): прокси, сборщик логов, обновлятор
конфигурации. Плохо другое — складывать в один под два независимых
приложения: они будут масштабироваться и обновляться только вместе.
Об этом в разделе 5.

ГЛАВНОЕ, ЧТО НАДО ЗАПОМНИТЬ ПРО ПОДЫ: под смертен и не воскресает.
Удалили под — он исчез. Упала нода — поды на ней не переедут. Именно
поэтому в реальной работе поды почти никогда не создают напрямую:
ими управляют Deployment, StatefulSet, Job. Но понимать под необходимо —
все остальные объекты в итоге создают именно поды.

Забегая вперёд: именно поэтому в учебных примерах мы создаём поды руками,
а в практике 4 перейдём на Deployment.

=========================================================================
1. Работа с подом через kubectl
=========================================================================

Посмотрим список подов в текущем namespace:
kubectl get pods

Пустой ответ — это нормально, если вы только что начали.

Создадим под командой, не описывая манифест:
kubectl run hello --image=YOUR_DOCKERHUB_LOGIN/k8sphp:version1

ЗАЧЕМ: kubectl run — быстрый способ поднять что-то одноразовое:
проверить образ, отладить сеть, выполнить разовую задачу. Для постоянной
работы он не годится: под, созданный так, ничем не управляется и не
восстановится после удаления.

ВАЖНО, ЧТО ИЗМЕНИЛОСЬ: до Kubernetes 1.18 эта команда создавала
Deployment. Начиная с 1.18 — просто под. Если найдёте старый мануал,
где написано обратное, он устарел.

ИСПРАВЛЕНО: раньше в команде стояла заглушка «наш образ из прошлого
занятия». kubectl не понимает подсказок: он попытается скачать образ
с буквальным именем и под уйдёт в ImagePullBackOff.

Проверим, что получилось:
kubectl get pods

Что вы увидите в выводе:
  NAME    READY   STATUS    RESTARTS   AGE
  hello   1/1     Running   0          15s

  READY 1/1 — значит «один контейнер из одного запущен». Именно поэтому
  формат записи такой: в поде может быть больше одного контейнера.
  RESTARTS показывает, сколько раз контейнер перезапускался. Значение
  больше 0 — повод разбираться.

Подробное описание пода:
kubectl describe pods hello

ЗАЧЕМ: это самая важная команда при разборе проблем. Она показывает всё
сразу: на какой ноде под, какой IP, какие ресурсы, состояния всех
контейнеров. И главное — в самом конце есть раздел Events, где видно,
что именно делал Kubernetes и на чём он споткнулся.

Читая вывод, обращайте внимание на три вещи: Node (где запущен),
Events (что происходило) и Limits/Requests (сколько ресурсов выделено).

Отправим одну команду внутрь пода, не заходя в него:
kubectl exec hello -- date

ЗАЧЕМ: удобно для быстрых проверок — посмотреть переменные окружения,
проверить доступность базы, посмотреть содержимое файла:
kubectl exec hello -- env
kubectl exec hello -- ls /var/www/html

Двойное тире -- отделяет команду kubectl от команды, которую выполняем
внутри контейнера. Без него kubectl попытается разобрать чужие флаги
как свои.

Войдём внутрь пода и останемся там:
kubectl exec -it hello -- sh

ЗАЧЕМ: -i включает ввод (interactive), -t выделяет терминал (tty).
По отдельности они бесполезны: без -t не будет приглашения строки, без -i
нельзя будет ничего напечатать. Обычно их пишут вместе.

Внутри можно осмотреться. Полезно посмотреть на сеть пода:
hostname -i          # это IP пода
ip addr

Выйти из шелла:
exit

Посмотреть логи:
kubectl logs hello

ЗАЧЕМ: логи — это то, что процесс пишет в stdout и stderr. Не в файлы
внутри контейнера, а именно в стандартные потоки. Kubernetes собирает
именно их. Многие начинающие ищут логи в /var/log внутри контейнера —
там их нет.

Следить за логами в реальном времени:
kubectl logs -f hello

Перенаправить порт на свой под:
kubectl port-forward hello 8080:80

ЗАЧЕМ: обратиться к поду напрямую снаружи нельзя: у него внутренний IP,
доступный только внутри кластера. port-forward открывает временный туннель
через API-сервер. Это приём для отладки, а не для эксплуатации: туннель
живёт, пока выполняется команда. Постоянный доступ даёт Service (практика 5).

Слева локальный порт, справа порт внутри пода. Теперь открываем в браузере
http://127.0.0.1:8080. Прервать — Ctrl+C.

Удалить под:
kubectl delete pod hello


=========================================================================
2. Создаём под через манифест
=========================================================================

mkdir -p ~/k8s
cd ~/k8s

ЗАЧЕМ МАНИФЕСТ, ЕСЛИ ЕСТЬ KUBECTL RUN: команда kubectl run — это одна
строчка. Реальный под описывают десятками параметров: ресурсы, пробы,
тома, политики безопасности. Никакой командой это не влезет. Кроме того,
манифест можно положить в git, отревьюить и применить повторно — то есть
он становится документацией вашей инфраструктуры.

# === файл: pod_web.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web
spec:
  containers:
    - name: container-apache
      image: YOUR_DOCKERHUB_LOGIN/k8sphp:version1
      ports:
        - containerPort: 80
# === конец файла ===

РАЗБЕРЁМ КАЖДОЕ ПОЛЕ, потому что этот каркас будет повторяться везде:

  apiVersion: v1 — какая версия API описывает объект. У каждого типа
    объекта она своя: у Pod это v1, у Deployment — apps/v1. Если указать
    не ту, kubectl скажет, что такого ресурса нет.

  kind: Pod — что именно мы создаём.

  metadata — «паспорт» объекта: имя, namespace, метки, аннотации.
    name должно быть уникальным в пределах namespace.

  spec — самое главное: описание ЖЕЛАЕМОГО состояния. Kubernetes будет
    добиваться, чтобы реальность совпала с этим описанием. В этом вся
    суть декларативного подхода: вы пишете «чего хочу», а не «что делать».

  containers — список контейнеров пода. У каждого обязательны два поля:
    name и image. Без image манифест отвергается с ошибкой
    «image: Required value».

  ports/containerPort — обратите внимание: этот параметр ничего не
    публикует наружу. Он носит справочный характер. Реальную доступность
    определяют Service и пробы.

Сохраняем и запускаем:
kubectl apply -f pod_web.yaml

ЧТО ДЕЛАЕТ APPLY: сравнивает то, что в файле, с тем, что уже есть
в кластере, и приводит второе к первому. Поэтому его можно выполнять
сколько угодно раз: объект не задублируется. Это и есть идемпотентность.

Полезный приём: посмотреть, что именно уйдёт в кластер, ничего не создавая:
kubectl apply -f pod_web.yaml --dry-run=client -o yaml

Проверяем:
kubectl get pods
kubectl describe pods my-web

Удалить под:
kubectl delete -f pod_web.yaml

ЗАЧЕМ УДАЛЯТЬ ПО ФАЙЛУ: так вы удаляете именно то, что описано в файле.
Удаление по имени (kubectl delete pod my-web) тоже работает, но легко
ошибиться в имени, а по файлу — нет.


=========================================================================
3. Меняем образ в манифесте
=========================================================================


nano pod_web.yaml
(в строке image заменить version1 на version2)

kubectl apply -f pod_web.yaml

ВАЖНО ПОНИМАТЬ: для пода это не «обновление», а замена. Под — неизменяемый
объект: Kubernetes не умеет менять образ у работающего пода. Он удалит
старый под и создаст новый. Никакого «без простоя» здесь нет и быть
не может — именно поэтому в реальной работе используют Deployment,
который умеет обновлять поды по одному (практика 4).

Убедимся в этом сами: сравните AGE и посмотрите события:
kubectl get pods
kubectl describe pods my-web | grep -i image

Удалить:
kubectl delete -f pod_web.yaml


=========================================================================
4. Под с метками (labels)
=========================================================================

ЗАЧЕМ НУЖНЫ МЕТКИ: метки — это пары ключ=значение, по которым объекты
находят друг друга. Service ищет свои поды не по имени, а по метке.
Deployment определяет «свои» поды тоже по метке. Имена подов меняются
(у пода из Deployment имя содержит случайный суффикс), а метки остаются —
поэтому связывать объекты по именам нельзя в принципе.

Метки бывают и у нод: по ним под выбирает, куда ему сесть.

# === файл: pod_web_v2_labels.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web
  labels:
    env: prod
    app: main
    tier: frontend
    owner: Engineer
spec:
  containers:
    - name: container-apache
      image: YOUR_DOCKERHUB_LOGIN/k8sphp:version1
      ports:
        - containerPort: 80
# === конец файла ===

Применяем и смотрим:
kubectl apply -f pod_web_v2_labels.yaml
kubectl get pods --show-labels

Выбрать поды по метке:
kubectl get pods -l env=prod
kubectl get pods -l tier=frontend

Операторы выборки — их полезно знать, они пригодятся и в Service, и в HPA:
  -l env=prod              равно
  -l env!=prod             не равно
  -l 'env in (prod,stage)' значение из списка
  -l tier                  метка вообще есть
  -l '!tier'               метки нет
  -l app=main,tier=frontend  условия через запятую = логическое И

Изменить метку у работающего пода:
kubectl label pod my-web env=staging --overwrite

Удалить под:
kubectl delete -f pod_web_v2_labels.yaml

ЧЕМ МЕТКА ОТЛИЧАЕТСЯ ОТ АННОТАЦИИ: и то, и другое — пары ключ-значение
в metadata. Но метки участвуют в выборках (по ним ищут объекты), а
аннотации — просто заметки, которые читает человек или инструмент.
Аннотациями, например, задают настройки Ingress-контроллеру.


=========================================================================
5. Под из двух контейнеров
=========================================================================

Само по себе несколько контейнеров в одном поде — приём
нормальный и постоянно используется (sidecar: прокси, сборщик логов,
обновлятор конфигурации). Плохая практика здесь в другом: в один под
поставлены два независимых приложения — веб-сервер и API. Они делят
общий IP и общий жизненный цикл, то есть масштабируются и обновляются
только вместе. Разные приложения нужно разносить по разным подам.

ИСПРАВЛЕНО: под в манифесте назывался my-web, а port-forward выполнялся
для пода my-app, которого не существовало. Теперь имя одно — my-app.

# === файл: pod_multi_container.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    env: prod
    app: main
    tier: frontend
    owner: Engineer
spec:
  containers:
    - name: container-web
      image: YOUR_DOCKERHUB_LOGIN/k8sphp:version1
      ports:
        - containerPort: 80

    - name: container-api
      image: tomcat:8.5.38
      ports:
        - containerPort: 8080
# === конец файла ===

Обратите внимание: порты у контейнеров РАЗНЫЕ (80 и 8080). Это требование,
а не пожелание: у контейнеров пода общий сетевой namespace, поэтому два
контейнера не могут слушать один и тот же порт — второй просто не сможет
запуститься.

Применяем:
kubectl apply -f pod_multi_container.yaml
kubectl get pod

Посмотреть на оба контейнера сразу:
kubectl get pod my-app -o jsonpath='{.spec.containers[*].name}'
kubectl logs my-app -c container-web     # флаг -c выбирает контейнер
kubectl logs my-app -c container-api

Смысл флага -c в том, что у пода несколько контейнеров, и kubectl надо
сказать, какой именно вы имеете в виду. Тот же флаг есть у exec.

ПРОВЕРКА ГЛАВНОГО СВОЙСТВА ПОДА — общего localhost. Зайдите в один
контейнер и обратитесь к другому по localhost:
kubectl exec -it my-app -c container-web -- sh
# внутри:
wget -qO- http://localhost:8080 | head -5
exit

Если tomcat уже поднялся, вы получите его страницу. Именно это и означает
«общий сетевой namespace».

Проверим доступность снаружи. Сначала веб-сервер на порту 80:
kubectl port-forward my-app 8080:80


Затем tomcat. Обратите внимание на порты: локальный 8081 ведём на 8080
внутри пода. В прежней версии было записано «порт 8080 на порт 80»,
то есть на порт php-контейнера, и tomcat так не открывался.
kubectl port-forward my-app 8081:8080

Удалить под:
kubectl delete -f pod_multi_container.yaml

ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ТО, ЧТО НУЖНО В РЕАЛЬНОЙ РАБОТЕ

Всё, что было выше, описывало под как таковой. Но под в таком виде

поэтому собирать ничего не нужно.


=========================================================================
6. Ресурсы: requests и limits
=========================================================================

ЗАЧЕМ: по умолчанию под может съесть всю память ноды, и тогда начнут
падать соседи. Лимиты — это способ сказать «столько тебе хватит».

Два разных параметра, которые постоянно путают:

  requests — сколько ГАРАНТИРОВАНО. Планировщик складывает requests всех
    подов и не поставит новый под на ноду, где суммы не помещаются.
    Это влияет на выбор ноды.

  limits — потолок, выше которого не пустят. Это влияет на работу
    уже запущенного контейнера.

# === файл: pod_resources.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-resources
  labels:
    app: my-web
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          cpu: 500m
          memory: 256Mi
# === конец файла ===

Про единицы измерения, чтобы не гадать:
  cpu: 100m — это 100 millicores, то есть 0.1 ядра. 1000m = 1 ядро.
    Дробные значения вроде 0.1 тоже допустимы, но запись в милликорах
    нагляднее;
  memory: 128Mi — мебибайты (1 Mi = 1024*1024 байт). Mi и M — это разные
    величины, и путать их не стоит.

ГЛАВНОЕ РАЗЛИЧИЕ В ПОВЕДЕНИИ ПРИ ПРЕВЫШЕНИИ:

  CPU — ресурс сжимаемый. Контейнер, упёршийся в лимит CPU, просто
        замедляется. Его никто не убивает.

  Память — ресурс несжимаемый. Память уже выделена процессу, «отобрать
        обратно» её нельзя. Поэтому при превышении лимита контейнер
        убивают. Это называется OOMKilled, и мы это увидим своими глазами
        в разделе 11.

Применяем:
kubectl apply -f manifests/03_pods/pod_resources.yaml
kubectl get pod my-web-resources

Посмотреть, сколько под реально потребляет, можно только с установленным
metrics-server (см. практику 4):
kubectl top pod my-web-resources

ПРО ПРАКТИКУ: requests ставят по результатам наблюдения за приложением,
а не «на глазок». Сначала смотрят, сколько оно ест в пике, и уже потом
назначают. Заниженный requests → нода перегружена и поды вытесняются.
Завышенный → половина кластера простаивает, а вы за неё платите.

Отдельная тема, которую стоит знать по названию: QoS-классы. По сочетанию
requests и limits под попадает в один из трёх классов, и от этого зависит,
кого вытеснят первым при нехватке памяти на ноде:
  Guaranteed — requests равны limits у всех контейнеров (самый защищённый);
  Burstable  — requests меньше limits (наш случай);
  BestEffort — ничего не задано вообще (вытеснят первым).


=========================================================================
7. Пробы: readiness, liveness, startup
=========================================================================

ЗАЧЕМ: без проб Kubernetes знает о контейнере ровно одно — процесс
запущен. Но «процесс запущен» и «приложение готово принимать запросы» —
это разные вещи. Приложение может стартовать полминуты, всё это время
отвечая ошибкой, а Service уже будет слать на него трафик, и пользователи
увидят 500-е.

Три вида проб, и у каждой своя задача:

  readinessProbe — «готов ли я принимать трафик». Пока проба не проходит,
    под исключается из эндпоинтов Service. Контейнер НЕ перезапускается.

  livenessProbe — «жив ли я». Проба перестала проходить — контейнер
    перезапускают. Лечит зависания, при которых процесс не падает.

  startupProbe — «я ещё только запускаюсь». Пока она не прошла, liveness
    и readiness не проверяются вообще. Нужна для медленно стартующих
    приложений, иначе liveness убьёт контейнер раньше, чем тот поднимется.

# === файл: pod_probes.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-probes
  labels:
    app: my-web
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
      startupProbe:
        httpGet:
          path: /
          port: 80
        failureThreshold: 30
        periodSeconds: 2
      readinessProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 2
        periodSeconds: 5
        failureThreshold: 3
      livenessProbe:
        httpGet:
          path: /
          port: 80
        initialDelaySeconds: 5
        periodSeconds: 10
        failureThreshold: 3
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
# === конец файла ===

Разберём параметры, потому что именно в них чаще всего ошибаются:
  initialDelaySeconds — пауза перед первой проверкой. Для startupProbe
    не нужна: она и так начинается сразу;
  periodSeconds — как часто проверять;
  failureThreshold — сколько неудач подряд считать провалом. Значение 3
    означает, что под уйдёт из балансировки не от одной случайной осечки;
  successThreshold — сколько успехов подряд нужно для возврата. Почти
    всегда 1;
  timeoutSeconds — сколько ждать ответа (по умолчанию 1 секунда, и этого
    иногда мало).

Применяем и смотрим:
kubectl apply -f manifests/03_pods/pod_probes.yaml
kubectl get pod my-web-probes

Проверить состояние проб руками:
kubectl describe pod my-web-probes | grep -A2 -E 'Liveness|Readiness|Startup'

Теперь самое поучительное — сломаем readiness и посмотрим, что будет.

Почему не через kubectl edit: под — неизменяемый объект. Большинство полей
спецификации пода после создания менять нельзя, и попытка поправить пробу
у работающего пода закончится ошибкой «field is immutable». Поэтому сделаем
копию манифеста с ДРУГИМ именем и поправим её:

cp manifests/03_pods/pod_probes.yaml ./pod_probes_broken.yaml
# в копии меняем ДВА поля:
#   metadata.name: my-web-probes -> my-web-probes-broken
#   readinessProbe.httpGet.path: / -> /not-found
kubectl apply -f ./pod_probes_broken.yaml

Имя обязательно менять: с прежним именем это была бы попытка изменить уже
существующий под, и API её отклонил бы.

Что вы увидите:
kubectl get pod my-web-probes-broken
# READY 0/1 — контейнер работает, но под не готов
kubectl describe pod my-web-probes-broken | grep -A5 Events

Ключевой момент: STATUS будет Running, а READY — 0/1. Контейнер жив,
но трафик на него не пойдёт. Если бы то же самое произошло с livenessProbe,
контейнер бы перезапускался, и в RESTARTS росли бы цифры. Разница
принципиальная, и именно её чаще всего не понимают.

ГЛАВНАЯ ОШИБКА НОВИЧКА: поставить liveness туда, где нужна readiness.
Приложение под нагрузкой отвечает медленнее обычного → liveness не
успевает → контейнер перезапускается → под нагрузкой он снова не успевает
→ бесконечный цикл перезапусков. Если видите, что поды перезапускаются
именно под нагрузкой, — в первую очередь проверьте livenessProbe.

Удалить:
kubectl delete -f manifests/03_pods/pod_probes.yaml
kubectl delete -f ./pod_probes_broken.yaml
rm -f ./pod_probes_broken.yaml


=========================================================================
8. ConfigMap: настройки отдельно от образа
=========================================================================

ЗАЧЕМ: настройки не должны быть запечены в образ. Иначе для смены адреса
базы данных придётся пересобирать и перепубликовывать образ — долго,
и один и тот же образ нельзя будет использовать на тесте и в проде.
ConfigMap хранит настройки отдельно, а образ остаётся неизменным.

ConfigMap НЕ подходит для секретов: содержимое хранится открытым текстом
и видно любому, у кого есть доступ к API. Пароли — только в Secret
(практика 7).

Создаём ConfigMap:

# === файл: configmap_app-config.yaml ===
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: prod
  APP_DEBUG: "false"
  APP_LOG_LEVEL: info
  app.properties: |
    db.host=postgres
    db.port=5432
    db.name=appdb
    cache.ttl=300
# === конец файла ===

Обратите внимание на две вещи:
  * APP_DEBUG: "false" — кавычки здесь обязательны. Без них YAML решит,
    что это логическое значение, а в ConfigMap допустимы только строки,
    и манифест будет отвергнут;
  * app.properties: | — вертикальная черта означает «сохранить переводы
    строк». Значение станет отдельным файлом, когда мы смонтируем ConfigMap
    томом.

Применяем:
kubectl apply -f manifests/03_pods/configmap_app-config.yaml
kubectl get configmap
kubectl describe configmap app-config

Обратите внимание: kubectl describe показывает содержимое целиком —
именно поэтому ConfigMap нельзя использовать для паролей.

Мы уже видели более короткий способ создать ConfigMap, без файла:
kubectl create configmap app-config --from-literal=APP_ENV=prod

СПОСОБ 1: ПЕРЕМЕННЫЕ ОКРУЖЕНИЯ

# === файл: pod_configmap_env.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-config-env
  labels:
    app: my-web
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      command: ["sh", "-c", "env | sort | grep '^APP_' ; sleep 3600"]
      envFrom:
        - configMapRef:
            name: app-config
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
# === конец файла ===

envFrom подставляет сразу ВСЕ ключи ConfigMap как переменные окружения.
У этого способа есть скрытая цена: если в ConfigMap появится ключ,
совпадающий с именем переменной внутри образа (например, PATH или HOME),
вы можете неожиданно сломать приложение. Для больших ConfigMap надёжнее
перечислять ключи явно:

      env:
        - name: ENVIRONMENT                # как назвать переменную
          valueFrom:
            configMapKeyRef:
              name: app-config             # откуда взять
              key: APP_ENV                 # какой ключ

Применяем и смотрим, что получилось:
kubectl apply -f manifests/03_pods/pod_configmap_env.yaml
kubectl logs my-web-config-env

ВАЖНОЕ ОГРАНИЧЕНИЕ: переменные окружения НЕ обновляются при изменении
ConfigMap. Контейнер придётся пересоздать. Сейчас убедимся в этом сами:

kubectl edit configmap app-config
# меняем APP_ENV: prod на APP_ENV: staging, сохраняем

Подождите минуту и проверьте снова:
kubectl logs my-web-config-env
# по-прежнему prod! Переменные не обновились.

Чтобы применить изменение, под надо пересоздать:
kubectl delete pod my-web-config-env
kubectl apply -f manifests/03_pods/pod_configmap_env.yaml
kubectl logs my-web-config-env
# теперь staging

СПОСОБ 2: ФАЙЛЫ НА ДИСКЕ

Многие приложения читают конфигурацию из файла, а не из переменных
окружения (nginx, postgres, prometheus). Для них ConfigMap монтируют томом —
каждый ключ становится отдельным файлом.

# === файл: pod_configmap_volume.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-config-volume
  labels:
    app: my-web
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      command: ["sh", "-c", "ls -l /etc/app ; cat /etc/app/app.properties ; sleep 3600"]
      volumeMounts:
        - name: config
          mountPath: /etc/app
          readOnly: true
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
  volumes:
    - name: config
      configMap:
        name: app-config
# === конец файла ===

Применяем и смотрим содержимое:
kubectl apply -f manifests/03_pods/pod_configmap_volume.yaml
kubectl logs my-web-config-volume

В отличие от переменных окружения, смонтированный том ОБНОВЛЯЕТСЯ сам,
когда ConfigMap меняется. Проверим:

kubectl edit configmap app-config
# меняем cache.ttl=300 на cache.ttl=600, сохраняем
# ждём примерно минуту (kubelet синхронизирует том не мгновенно)
kubectl exec my-web-config-volume -- cat /etc/app/app.properties

Значение изменилось без пересоздания пода. Приложению остаётся перечитать
конфигурацию — некоторые умеют это сами, некоторым нужен сигнал
(для nginx это nginx -s reload).

ВАЖНОЕ ИСКЛЮЧЕНИЕ: автоматическое обновление НЕ работает, если монтировать
отдельный файл через subPath — такой файл «застывает» на моменте старта
контейнера. Это ограничение самого Kubernetes, и оно часто застаёт врасплох.

Удалить:
kubectl delete -f manifests/03_pods/pod_configmap_volume.yaml
kubectl delete -f manifests/03_pods/pod_configmap_env.yaml


=========================================================================
9. Init-контейнеры
=========================================================================

ЗАЧЕМ: иногда до старта основного приложения нужно что-то сделать:
дождаться базы данных, подготовить файлы, применить миграции, скачать
конфигурацию. Init-контейнер выполняется ДО основных и должен успешно
завершиться. Пока он не отработал, основные контейнеры не запустятся.

ЧЕМ ОТЛИЧАЕТСЯ ОТ ОБЫЧНОГО КОНТЕЙНЕРА В ПОДЕ:
  * init-контейнеры идут строго по очереди, а обычные — параллельно;
  * они обязаны завершиться (для постоянно работающего помощника, например
    прокси, используют обычный контейнер);
  * к ним не применяются пробы readiness и liveness.

# === файл: pod_init_container.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-init
  labels:
    app: my-web
spec:
  initContainers:
    - name: prepare-content
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo '<h1>Content created by init container</h1>' > /workdir/index.html
          ls -l /workdir
      volumeMounts:
        - name: workdir
          mountPath: /workdir
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 100m
          memory: 64Mi
  containers:
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
      volumeMounts:
        - name: workdir
          mountPath: /usr/share/nginx/html
          readOnly: true
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
  volumes:
    - name: workdir
      emptyDir: {}
# === конец файла ===

Как здесь передаются данные: init-контейнер пишет файл в том workdir,
основной контейнер монтирует тот же том в каталог, откуда nginx отдаёт
страницы. emptyDir — временный том, который живёт ровно столько же,
сколько под.

Применяем и наблюдаем за порядком запуска:
kubectl apply -f manifests/03_pods/pod_init_container.yaml

Полезный приём: смотреть изменения в реальном времени (флаг -w, watch):
kubectl get pod my-web-init -w

Вы увидите последовательность: Init:0/1 → PodInitializing → Running.
Пока init-контейнер не завершится, основной не начнёт запускаться.

Посмотреть логи init-контейнера:
kubectl logs my-web-init -c prepare-content

Убедиться, что контент действительно создан init-контейнером:
kubectl exec my-web-init -- cat /usr/share/nginx/html/index.html

Удалить:
kubectl delete -f manifests/03_pods/pod_init_container.yaml


=========================================================================
10. securityContext: запуск не от root
=========================================================================

ЗАЧЕМ: по умолчанию контейнеры запускаются от root. Если злоумышленник
проэксплуатирует уязвимость в приложении, он получит root внутри
контейнера и попробует выйти на ноду. Запуск от непривилегированного
пользователя сильно сокращает возможности такой атаки.

Есть и вторая причина, вполне практическая: политики безопасности кластера
(Pod Security Admission) в режиме restricted просто не дадут запустить под
от root. В кластерах посерьёзнее это требование по умолчанию, поэтому
привыкать стоит сразу.

ПРО ГОТОВЫЙ ОБРАЗ. Обычный nginx запускается от root и слушает порт 80:
непривилегированный процесс не может занять порт ниже 1024. Поэтому
используем официальный образ nginxinc/nginx-unprivileged — он уже настроен
работать от пользователя 101 и слушать порт 8080. Для популярных
приложений почти всегда есть такой «unprivileged» вариант.

# === файл: pod_security_context.yaml ===
apiVersion: v1
kind: Pod
metadata:
  name: my-web-secure
  labels:
    app: my-web
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 101
    runAsGroup: 101
    fsGroup: 101
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: web
      image: nginxinc/nginx-unprivileged:1.27-alpine
      ports:
        - containerPort: 8080
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
      volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: cache
          mountPath: /var/cache/nginx
      resources:
        requests:
          cpu: 50m
          memory: 64Mi
        limits:
          cpu: 200m
          memory: 128Mi
  volumes:
    - name: tmp
      emptyDir: {}
    - name: cache
      emptyDir: {}
# === конец файла ===

Что означает каждый параметр:

  runAsNonRoot: true — запрет на запуск от root. Если образ всё равно
    пытается стартовать от uid 0, под не запустится с ошибкой
    «container has runAsNonRoot and image will run as root». Это не баг,
    а именно то, чего мы добивались;
  runAsUser / runAsGroup — под каким uid/gid работать;
  fsGroup — группа-владелец смонтированных томов. Нужна, чтобы контейнер
    мог писать в том, не будучи его владельцем;
  seccompProfile: RuntimeDefault — стандартный профиль seccomp, который
    ограничивает набор доступных контейнеру системных вызовов;
  allowPrivilegeEscalation: false — запрет получать дополнительные
    привилегии (закрывает, в частности, классический трюк через setuid);
  capabilities.drop: [ALL] — убираем все Linux-возможности. По умолчанию
    контейнеру выдают набор capabilities, которые ему почти никогда
    не нужны;
  readOnlyRootFilesystem: true — корневая файловая система только для
    чтения. Злоумышленник не сможет подменить бинарники или дописать
    скрипт в автозапуск.

Обратите внимание: раз корневая ФС только для чтения, каталоги, в которые
nginx обязан писать, вынесены на отдельные временные тома. Это обычная
цена read-only: приложению нужно явно указать, куда ему разрешено писать.

Применяем:
kubectl apply -f manifests/03_pods/pod_security_context.yaml
kubectl get pod my-web-secure

Проверим, что контейнер действительно работает не от root:
kubectl exec my-web-secure -- id
# uid=101 gid=101 — не root

Проверить, что корневая ФС только для чтения, можно так:
kubectl exec my-web-secure -- touch /test-file
# touch: /test-file: Read-only file system

Если под не стартует — посмотрите его логи. При переходе на read-only
приложению может понадобиться ещё один записываемый каталог; это
нормальный итеративный процесс, а не признак того, что вы всё сломали.

Удалить:
kubectl delete -f manifests/03_pods/pod_security_context.yaml


=========================================================================
11. Учимся разбирать поломки
=========================================================================

Это, пожалуй, самый полезный раздел практики. В реальной работе вы будете
разбирать такие ситуации постоянно, и умение читать состояние пода
и события ценится выше, чем знание всех полей манифеста.

Применяем четыре намеренно сломанных пода сразу:
kubectl apply -f manifests/03_pods/pod_broken_examples.yaml

Подождите 30-60 секунд, чтобы состояния устоялись, и посмотрите:
kubectl get pods -l purpose=troubleshooting

Ожидаемая картина:
  NAME             READY   STATUS             RESTARTS
  broken-image     0/1     ImagePullBackOff   0
  broken-command   0/1     CrashLoopBackOff   4
  broken-oom       0/1     OOMKilled          3
  broken-pending   0/1     Pending            0

Теперь разберём каждую по очереди.

-------------------------------------------------------------------
СЛУЧАЙ 1: ImagePullBackOff — не могу скачать образ
-------------------------------------------------------------------

kubectl describe pod broken-image

Смотрим в самый низ, в раздел Events:
  Warning  Failed   Failed to pull image "nginx:1.27-alpine-ops": ...
           manifest unknown
  Warning  Failed   Error: ErrImagePull
  Normal   BackOff  Back-off pulling image "nginx:1.27-alpine-ops"

Причина прямо в тексте: manifest unknown — тега с таким именем
в реестре нет. В нашем случае в теге опечатка.

Что проверять при ImagePullBackOff, по порядку:
  1) нет ли опечатки в имени образа и теге (наш случай);
  2) правильный ли реестр и существует ли образ там вообще;
  3) нужен ли доступ: образ приватный, а imagePullSecrets не указан —
     тогда в событиях будет 401 Unauthorized или pull access denied;
  4) не мешает ли сеть: если в событиях timeout или no such host,
     проблема в доступе ноды к реестру, а не в имени образа.

Слово BackOff означает растущую паузу между попытками, а не «откат».
kubelet пробует снова и снова, каждый раз увеличивая интервал.

-------------------------------------------------------------------
СЛУЧАЙ 2: CrashLoopBackOff — контейнер падает при старте
-------------------------------------------------------------------

kubectl describe pod broken-command
kubectl logs broken-command

Логи покажут:
  ERROR: cannot connect to database at postgres:5432

ВОТ ЗДЕСЬ ГЛАВНАЯ ЛОВУШКА. Если контейнер уже успел перезапуститься,
обычный kubectl logs может показать пустоту или логи нового запуска.
Логи предыдущего запуска достаются отдельно:
kubectl logs broken-command --previous

Запомните этот флаг: без него в половине случаев вы не увидите причину.

Код возврата смотрим так:
kubectl get pod broken-command -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'

Что проверять при CrashLoopBackOff:
  1) логи текущего и предыдущего запуска (kubectl logs, затем --previous);
  2) код возврата: 1 — приложение само упало, 137 — убито (OOM или SIGKILL),
     143 — остановлено по SIGTERM;
  3) правильно ли заданы command и args в манифесте;
  4) если приложение требует конфигурацию —нет ли ошибки
     «config not found», «permission denied».

Полезная практика: чтобы разбираться было проще, на время отладки
поставьте restartPolicy: Never — контейнер упадёт и останется в состоянии
Error, вместо бесконечного цикла перезапусков.

-------------------------------------------------------------------
СЛУЧАЙ 3: OOMKilled — превышен лимит памяти
-------------------------------------------------------------------

kubectl describe pod broken-oom

В разделе Last State увидите:
  Reason: OOMKilled
  Exit Code: 137

137 = 128 + 9, где 9 — сигнал SIGKILL. Если видите 137, почти всегда это
либо лимит памяти у контейнера, либо нехватка памяти на самой ноде.

Проверить лимит:
kubectl get pod broken-oom -o jsonpath='{.spec.containers[0].resources}'

Что делать при OOMKilled:
  1) посмотреть реальное потребление приложения (kubectl top pod, если
     установлен metrics-server);
  2) либо поднять лимит памяти, либо чинить утечку в приложении.
     Простое поднятие лимита без анализа — лечить симптом;
  3) помнить, что requests и limits по памяти должны быть реалистичными:
     приложение может требовать больше при старте, чем в работе.

ВАЖНОЕ НАБЛЮДЕНИЕ: сравните эту ситуацию с CPU. Если бы мы упёрлись
в лимит CPU, контейнер продолжил бы работать, просто медленнее.
Память так не работает — её отбирают вместе с жизнью контейнера.

-------------------------------------------------------------------
СЛУЧАЙ 4: Pending — планировщик не может найти место
-------------------------------------------------------------------

kubectl describe pod broken-pending

В событиях:
  Warning  FailedScheduling  default-scheduler  0/3 nodes are available:
  3 Insufficient cpu. preemption: 0/3 nodes are available: ...

Читается буквально: на трёх нодах не хватает CPU. Мы запросили 100 ядер
requests, и планировщик честно не нашёл, куда поставить под.

Важно: Pending означает «под ещё не запущен», а не «под сломался».
Контейнер вообще не создавался, поэтому и логов нет.

Что проверять при Pending:
  1) events пода — там всегда написана причина (Insufficient cpu/memory);
  2) свободные ресурсы нод:
     kubectl describe node ИМЯ_НОДЫ | grep -A8 'Allocated resources';
  3) nodeSelector или affinity — не требует ли под метку, которой
     ни у одной ноды нет;
  4) taints на нодах:
     kubectl describe node ИМЯ_НОДЫ | grep -i taint;
  5) если под использует PVC — не ждёт ли он связывания с томом
     (практика 6, это тоже даёт Pending).

-------------------------------------------------------------------
ОБЩИЙ АЛГОРИТМ РАЗБОРА
-------------------------------------------------------------------

Запомните эту последовательность, она выручает почти всегда:

  1. kubectl get pods
     Смотрим STATUS. Из него уже понятно направление поиска.

  2. kubectl describe pod ИМЯ
     Читаем EVENTS в самом низу. В 80% случаев причина написана там
     прямым текстом. Это первое, что нужно смотреть.

  3. kubectl logs ИМЯ
     Если контейнер запускался — смотрим, что он успел сказать.

  4. kubectl logs ИМЯ --previous
     Если контейнер перезапускался — смотрим логи предыдущего запуска.

  5. kubectl exec -it ИМЯ -- sh
     Если контейнер работает, но ведёт себя странно — заходим внутрь.

  6. kubectl get events --sort-by=.lastTimestamp
     События по всему namespace в хронологическом порядке. Полезно,
     когда непонятно, с чего вообще началось.

Соответствие состояния и причины — шпаргалка:
  ImagePullBackOff / ErrImagePull — проблемы с образом: имя, тег, доступ, сеть
  CrashLoopBackOff  — приложение падает при старте, смотреть логи
  OOMKilled         — превышен лимит памяти
  Pending           — планировщик не нашёл ноду
  ContainerCreating — kubelet готовит контейнеры (тома, секреты, сеть)
  Terminating       — под удаляется, но не может завершиться (часто из-за
                      тома или finalizer, помогает --force --grace-period=0)
  Evicted           — под вытеснен с ноды из-за нехватки ресурсов

Удалить все сломанные поды:
kubectl delete -f manifests/03_pods/pod_broken_examples.yaml


=========================================================================
12. Полезные приёмы kubectl
=========================================================================

Небольшая подборка команд, которые заметно ускоряют работу. Их стоит
запомнить, они пригодятся во всех следующих практиках.

ВСТРОЕННАЯ СПРАВКА. Не нужно гуглить поля манифеста:
kubectl explain pod
kubectl explain pod.spec.containers
kubectl explain pod.spec.containers.resources
kubectl explain pod.spec.containers.livenessProbe --recursive

Это локальная документация по той версии API, которая стоит в кластере.
Точнее любого старого мануала из интернета.

ПОДРОБНЫЙ ВЫВОД:
kubectl get pods -o wide

Добавляет IP пода и имя ноды — сразу видно, что где живёт.

СЛЕЖЕНИЕ ЗА ИЗМЕНЕНИЯМИ:
kubectl get pods -w

Полезно, когда применяете манифест и хотите увидеть, как под проходит
все стадии: Pending → ContainerCreating → Running.

ВЫБОРКА ПОЛЕЙ ЧЕРЕЗ JSONPATH:
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\n"}{end}'

Таблицей, с нужными вам колонками:
kubectl get pods -o custom-columns='NAME:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP'

Эти два приёма особенно выручают в скриптах и в практике RBAC, где нужно
проверить права конкретного пользователя.

СОБЫТИЯ В ПОРЯДКЕ ВОЗНИКНОВЕНИЯ:
kubectl get events --sort-by=.lastTimestamp
kubectl get events --field-selector involvedObject.name=my-web

События живут ограниченное время (обычно час), поэтому разбирать поломку
лучше сразу, а не на следующий день.

РЕСУРСЫ НОД — куда ещё можно поставить под:
kubectl describe node ИМЯ_НОДЫ | grep -A8 'Allocated resources'

Показывает, сколько requests уже занято и сколько осталось.

КОПИРОВАНИЕ ФАЙЛОВ В ПОД И ИЗ ПОДА:
kubectl cp ./index.php my-web:/tmp/index.php
kubectl cp my-web:/etc/nginx/nginx.conf ./nginx.conf

Удобно для отладки: посмотреть реальный конфиг внутри контейнера.

ПЕРЕЗАПУСК БЕЗ ПОСТОРОННИХ ПОДОВ (пригодится в практике 4):
kubectl rollout restart deployment ИМЯ

УДАЛЕНИЕ С ОЖИДАНИЕМ:
kubectl delete pod my-web --grace-period=30

Приложение получает SIGTERM и 30 секунд на корректное завершение
(закрыть соединения, дописать данные). Значение по умолчанию — тоже 30,
и уменьшать его без нужды не стоит. Жёсткое удаление без ожидания:
kubectl delete pod my-web --force --grace-period=0
