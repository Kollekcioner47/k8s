Практика 11. RBAC: кто и что может делать в кластере.

Готовые манифесты к этой практике лежат в manifests/app_4_rbac/.


=========================================================================
ЗАЧЕМ НУЖЕН RBAC
=========================================================================

До сих пор мы работали с кластером от имени администратора. Мы могли
всё: удалить чужие namespace, прочитать любой секрет, изменить системные
компоненты. Для учебного стенда это удобно, в реальной работе — недопустимо.

Причины вполне практические:

  * РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ. Разработчик не должен иметь возможности
    удалить namespace с базой данных. Администратор базы — трогать
    системные компоненты кластера;
  * ЗАЩИТА СЕКРЕТОВ. Право читать секреты означает право знать пароли.
    Мы разбирали это в практике 7: RBAC — одна из двух вещей, которые
    реально защищают секреты;
  * КОНТРОЛЬ ДОСТУПА ПРИЛОЖЕНИЙ. Приложению в кластере тоже нужны права,
    если оно обращается к API. Обычно — очень ограниченные, и это
    отдельная задача;
  * ТРЕБОВАНИЯ АУДИТА. На вопрос «кто может удалить прод» должен быть
    точный ответ, а не «вроде все админы».

КЛЮЧЕВАЯ ОСОБЕННОСТЬ KUBERNETES, КОТОРАЯ УДИВЛЯЕТ ВСЕХ

В Kubernetes НЕТ своей базы пользователей. Совсем нет. Нет списка логинов,
нет паролей, нет групп внутри кластера. Посмотреть «всех пользователей»
командой невозможно — их негде хранить.

Пользователь для Kubernetes — это просто НЕКОЕ ИМЯ, которое API-сервер
извлёк из предъявленного удостоверения. Удостоверением может быть:
  * клиентский сертификат — имя берётся из поля CN, группы из полей O;
  * токен OIDC — имя и группы приходят из токена внешнего провайдера;
  * обычная пара логин-пароль из файла htpasswd (в наши дни почти не
    используется);
  * токен ServiceAccount — для приложений и автоматизации.

RBAC работает уже с этим именем и группами. Он отвечает не на вопрос
«кто ты», а на вопрос «что тебе разрешено» — отвечает на него аутентификация.

ОТСЮДА СЛЕДУЕТ ПРАКТИЧЕСКИЙ ВЫВОД, КОТОРЫЙ СТОИТ ЗАПОМНИТЬ: чтобы
«добавить пользователя в Kubernetes», нельзя выполнить одну команду.
Нужно выпустить ему удостоверение (обычно сертификат), настроить kubectl
и выдать права через RBAC. Именно так мы и сделаем в разделе 7 части 2.

ПОДОВ И ПРИЛОЖЕНИЙ ЭТО ТОЖЕ КАСАЕТСЯ: приложение внутри кластера —
такой же «пользователь», только со своим способом опознания.
И есть популярное заблуждение, что «под работает с правами сервис-аккаунта».
Про него подробно в разделе 4.

=========================================================================
1. Смотрим ServiceAccount
=========================================================================

Перейдём в консоль и посмотрим список ServiceAccount:
kubectl get serviceaccount

Видим ServiceAccount default. Свой сервис-аккаунт default есть в каждом
namespace, он создаётся автоматически. По умолчанию прав на доступ к API
у этого аккаунта нет никаких.

ЗАЧЕМ ВООБЩЕ SERVICEACCOUNT: у пользователей есть люди, которые могут
ввести логин и пароль. У приложения такой возможности нет — оно не может
«залогиниться». ServiceAccount — это учётная запись для программы:
опознаётся по токену, который Kubernetes выдаёт и монтирует в под
автоматически.

Смотрим внутрь:
kubectl get sa default -o yaml

Видим служебные поля и имя. Имя — это то, что мы указываем при создании
ServiceAccount.

Заодно посмотрим, сколько аккаунтов вообще есть в кластере:
kubectl get sa -A

Обратите внимание: в системных namespace их много. Это не ваши аккаунты,
а учётные записи компонентов кластера: контроллеров, планировщика,
сетевого плагина. Каждый компонент ходит в API под своим именем и имеет
ровно те права, которые ему нужны. Это и есть RBAC в действии.


=========================================================================
2. ИСПРАВЛЕНО: поле secret и токен
=========================================================================

В прежней версии этого файла было сказано: «В поле secret лежит название
секрета с токеном. Это поле добавляется контроллером автоматически».

Это было верно до Kubernetes 1.24. Начиная с 1.24 поведение изменилось:
ServiceAccount больше НЕ получает автоматически секрет с токеном, и поля
secret в его описании нет вообще. Убедиться можно так:

kubectl get sa default -o yaml | grep -i secret
# ничего не выведет

КАК УСТРОЕН ТОКЕН ТЕПЕРЬ

  * вместо долгоживущего секрета kubelet монтирует в поды так называемый
    projected token — короткоживущий токен с ограниченным сроком действия,
    который автоматически обновляется;
  * внутри контейнера он по-прежнему доступен по пути
    /var/run/secrets/kubernetes.io/serviceaccount/token;
  * рядом лежат ca.crt (корневой сертификат кластера — по нему клиент
    убеждается, что говорит именно с нужным кластером) и файл namespace.

Проверить в любом запущенном поде:
kubectl exec -it ИМЯ_ПОДА -- ls -l /var/run/secrets/kubernetes.io/serviceaccount/

ЗАЧЕМ БЫЛО МЕНЯТЬ: старый токен был бессрочным. Он лежал в секрете,
жил годами и не отзывался: если он утекал, злоумышленник имел доступ
к API до тех пор, пока кто-то вручную не удалит секрет. Новый токен
привязан к конкретному поду, имеет срок действия и аудиторию, и его
невозможно использовать, если под удалён.

Если всё же нужен долгоживущий токен — например, для внешней системы,
которая не умеет обновлять токен сама, — его запрашивают явно:

kubectl create token default --duration=24h

ДОБАВЛЕНО, это стоит проговорить: у команды есть параметр --audience.
Аудитория ограничивает, кому токен можно предъявлять. Для внешних систем
указывайте конкретную аудиторию, а не оставляйте значение по умолчанию —
тогда утекший токен нельзя будет использовать для доступа к API кластера.

Либо создают секрет типа service-account-token вручную — но это уже
осознанное понижение безопасности, а не поведение по умолчанию.

Токен передаётся в заголовках HTTP-запроса к API-серверу:
    Authorization: Bearer <токен>


=========================================================================
3. ServiceAccount в поде
=========================================================================

Вы можете создать свой сервис-аккаунт и указать его имя в манифесте пода.
Тогда при запуске контейнеров пода в них будет смонтирован токен от этого
аккаунта. Если ServiceAccount не указывать, монтируется токен аккаунта
default.

kubectl create serviceaccount my-app-sa

Использование в поде:
    spec:
      serviceAccountName: my-app-sa
      containers:
        - name: app
          image: nginx

Обратите внимание: монтирование токена можно и вовсе отключить, если
приложению API не нужно. Это уменьшает поверхность атаки:
    spec:
      automountServiceAccountToken: false

ЗАЧЕМ ОТКЛЮЧАТЬ ТОКЕН, ЕСЛИ ОН И ТАК БЕЗ ПРАВ: сам по себе токен прав
не даёт, но он опознаёт под. Ошибка в RBAC-привязке — или привязка,
сделанная «на будущее» кем-то другим — немедленно превращает его
в рабочий инструмент. Если у приложения токена нет, украсть его нельзя.

Проверить, что токен не смонтирован:
kubectl exec -it ИМЯ_ПОДА -- ls /var/run/secrets/kubernetes.io/serviceaccount/
# No such file or directory — вот что мы хотим увидеть

ПРАВИЛО, КОТОРОЕ СТОИТ ЗАПОМНИТЬ: по умолчанию монтирование включено,
и это историческое поведение. В новом кластере разумно сразу отключать
его на уровне отдельного ServiceAccount для приложений, которым API
не нужен.


=========================================================================
4. Частое заблуждение
=========================================================================

Иногда говорят, что «под работает с правами сервис-аккаунта». Это приводит
к путанице и мешает понять принципы работы.

Под нигде не «работает». Работает приложение. Приложение запущено
в контейнерах пода на воркер-узлах и работает там как обычный
Linux-процесс в изоляции. Всё.

Единственное, что делает Kubernetes — kubelet монтирует токен внутрь
контейнеров. Дальше приложение само решает: если ему нужно обращаться
к API кластера, возьмёт ли оно токен из этого смонтированного файла
или воспользуется другим способом аутентификации.

Иными словами, наличие смонтированного токена само по себе ничего
не разрешает и ничего не нарушает: права определяются RBAC-привязками
для этого ServiceAccount.

ПОЧЕМУ ЭТО РАЗЛИЧЕНИЕ ПРАКТИЧНО ВАЖНО: из него следует, что защита
приложения и защита кластера — разные задачи. Можно выдать приложению
минимум прав через RBAC, но если приложение уязвимо и через него выполнят
произвольный код, злоумышленник получит ровно те права, которые были
у ServiceAccount. Поэтому «дать побольше, чтобы работало» — плохая идея:
вы расширяете не удобство, а возможности атакующего.

=========================================================================
5. Основные компоненты RBAC
=========================================================================

Четыре объекта, и их важно не путать:

  Role — набор разрешений в пределах одного namespace.
  ClusterRole — набор разрешений на уровне всего кластера.
  RoleBinding — связывает субъект с Role (или с ClusterRole, но только
    в пределах одного namespace).
  ClusterRoleBinding — связывает субъект с ClusterRole на весь кластер.

СУБЪЕКТЫ, на которые можно выдать права (поле subjects):
  kind: User          — пользователь, имя из сертификата или OIDC;
  kind: Group         — группа, тоже из сертификата (поле O) или OIDC;
  kind: ServiceAccount — учётная запись приложения.

САМОЕ ГЛАВНОЕ, ЧТО НАДО ПОНЯТЬ ПРО ЭТУ СХЕМУ: Role и ClusterRole сами
по себе НИЧЕГО никому не разрешают. Это просто списки прав, как рецепт
без повара. Пока нет привязки (Binding), они бесполезны. Именно поэтому
в кластере можно спокойно создавать роли «про запас» — вреда не будет.

И ещё: привязка ссылается на роль ПО ИМЕНИ и не проверяет её существование
при создании. Опечатка в имени роли приводит к тому, что привязка есть,
роль есть, а прав нет. Об этом подробно в разделе 12.

ЧТО ВЫБРАТЬ — ROLE ИЛИ CLUSTERROLE. Простое правило: если объект
принадлежит namespace (поды, сервисы, деплойменты, секреты, конфигмапы) —
используйте Role. ClusterRole нужен для объектов, которые в принципе
кластерные: ноды, persistentvolumes, storageclasses, namespaces.
Список таких объектов разбирается в manifests/app_4_rbac/clusterrole-node-reader.yaml.

ЕСТЬ И ТРЕТИЙ ВАРИАНТ, САМЫЙ НЕДООЦЕНЁННЫЙ: ClusterRole плюс RoleBinding.
Список прав составляется один раз, а область действия задаётся привязкой —
получаются те же права, но только в одном namespace. Так выдают, например,
права на чтение разработчику в его namespace, используя готовую
ClusterRole view:

    kubectl create rolebinding dev-view \
      --clusterrole=view --user=developer --namespace=team-a


=========================================================================
6. Проверяем права: команды, которые надо знать
=========================================================================

Прежде чем выдавать права, полезно уметь их проверять. Три команды,
которые используются постоянно.

ЧТО МОГУ Я САМ:
kubectl auth can-i create deployments
kubectl auth can-i '*' '*' --all-namespaces     # не админ ли я часом

ПОЛНЫЙ СПИСОК МОИХ ПРАВ:
kubectl auth can-i --list
kubectl auth can-i --list --namespace=kube-system

Вывод читается как таблица «какие ресурсы и какие действия разрешены».
Полезно, когда непонятно, откуда взялись права: там видно, какая роль
их дала.

ПРАВА ДРУГОГО СУБЪЕКТА (имперсонация):
kubectl auth can-i list pods --as=system:serviceaccount:default:ci-deployer
kubectl auth can-i create deployments --as=system:serviceaccount:default:ci-deployer

ЗАЧЕМ ЭТО НУЖНО НА ПРАКТИКЕ: так проверяют настройку CI/CD перед запуском
конвейера. Гораздо приятнее узнать о нехватке прав одной командой, чем
из упавшего на середине выката.

ВАЖНАЯ ОГОВОРКА: имперсонация выполняется ВАШИМИ правами администратора.
То есть команда с --as проверяет только правила RBAC и ничего не говорит
о том, сможет ли субъект аутентифицироваться. Если сертификат пользователя
выпущен неправильно, эта проверка всё равно покажет ожидаемый результат.
Поэтому в разделе 7 мы проверим доступ по-настоящему — с сертификатом.

Как формируется имя ServiceAccount в поле --as: это
system:serviceaccount:<namespace>:<имя>. Запомнить полезно — без префикса
команда не найдёт аккаунт.


=========================================================================
7. Создаём пользователя: сертификат и kubeconfig
=========================================================================

Это полный разбор того, как в Kubernetes заводят человека. Раньше в курсе
это было в отдельной практике; здесь мы совмещаем теорию и практику.

ВАЖНО СРАЗУ ПОНЯТЬ: команда useradd НЕ добавляет пользователя
в Kubernetes. Она создаёт обычного пользователя Linux, в домашнем каталоге
которого мы будем хранить ключ. С тем же успехом файлы можно держать
где угодно. В кластере пользователя как объекта не существует.

1. Создаём пользователя ОС (только как место для ключей):

sudo useradd -m k8suser
sudo passwd k8suser
sudo su - k8suser

Флаг -m нужен, иначе домашний каталог не создастся. Все дальнейшие команды
выполняем от имени k8suser, чтобы файлы ключей не принадлежали root.

2. Генерируем ключ и запрос на подпись сертификата (CSR):

openssl genrsa -out k8suser.key 2048
openssl req -new -key k8suser.key -out k8suser.csr -subj "/CN=k8suser/O=developers"

Поля здесь не декоративные, а несущие:
  CN (Common Name) станет ИМЕНЕМ пользователя в Kubernetes;
  O (Organization) станет его ГРУППОЙ.
Именно эти значения указываются потом в subjects у RoleBinding.
Никакой другой связи с пользователем ОС нет.

3. Подписываем сертификат корневым CA кластера:

sudo openssl x509 -req -in k8suser.csr -CA /etc/kubernetes/pki/ca.crt -CAkey /etc/kubernetes/pki/ca.key -CAcreateserial -out k8suser.crt -days 365

sudo нужен потому, что приватный ключ CA доступен только root.
Сертификат выдан на 365 дней: по истечении доступ пропадёт, и его придётся
перевыпускать. Это не недоработка, а защита: утёкший сертификат конечен
по времени жизни.

4. Добавляем пользователя в конфигурацию kubectl:

Две правки против прежней версии практики:

  * добавлен флаг --embed-certs=true. Без него в kubeconfig попадут только
    ПУТИ к файлам сертификата, и конфиг перестанет работать при переносе
    на другую машину или запуске из другого каталога;
  * имя кластера берётся из текущего kubeconfig, а не подставляется
    жёстко как «kubernetes» — у кластера может быть любое имя.

CLUSTER=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}')

kubectl config set-credentials k8suser \
  --client-certificate=k8suser.crt \
  --client-key=k8suser.key \
  --embed-certs=true

kubectl config set-context k8suser-context \
  --cluster="$CLUSTER" \
  --user=k8suser \
  --namespace=default

Проверяем, какие контексты получились:
kubectl config get-contexts

5. Проверяем аутентификацию ДО выдачи прав:

kubectl --context=k8suser-context auth can-i list pods
# no — пользователь опознан, но прав пока нет

ВОТ ЭТО И ЕСТЬ ГЛАВНАЯ ПРОВЕРКА, которой не было в прежней практике.
Команда вернула «no», а не «error: You must be logged in». Это значит,
что сертификат принят, пользователь k8suser опознан, и теперь дело
только за правами. Если бы сертификат был выпущен неправильно, мы бы
увидели ошибку аутентификации — и это гораздо понятнее, чем гадать,
почему «права вроде выданы, а не работает».


=========================================================================
8. Выдаём права и проверяем их по-настоящему
=========================================================================

1. Роль:

# === файл: role.yaml ===
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: k8suser-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
# === конец файла ===

Пустая строка в apiGroups: [""] — это core-группа: pods, services, secrets
и другие базовые объекты. Для Deployment здесь было бы ["apps"].

2. Привязка:

# === файл: rolebinding.yaml ===
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: k8suser-binding
  namespace: default
subjects:
  - kind: User
    name: k8suser
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: k8suser-reader
  apiGroup: rbac.authorization.k8s.io
# === конец файла ===

Значение name в subjects должно ТОЧНО совпадать с CN в сертификате.
Опечатка или другой регистр — и прав не будет, при этом никакой ошибки
вы не увидите: доступ просто окажется запрещён.

3. Применяем:

kubectl apply -f manifests/app_4_rbac/role.yaml
kubectl apply -f manifests/app_4_rbac/rolebinding.yaml

4. Проверяем доступ. Способ первый — по правилам, имперсонацией:

kubectl auth can-i list pods --as=k8suser
# yes

kubectl auth can-i delete pods --as=k8suser
# no

Способ второй — по-настоящему, с сертификатом:

kubectl --context=k8suser-context auth can-i list pods
# yes
kubectl --context=k8suser-context get pods
# показывает список подов

Вот это уже настоящая проверка: kubectl аутентифицируется тем самым
сертификатом, который мы подписали.

Проверяем запрет на практике, а не только через can-i:
kubectl --context=k8suser-context delete pod ИМЯ_ПОДА
# Error from server (Forbidden): ... cannot delete resource "pods"

Обратите внимание на формулировку ошибки: Forbidden, а не Unauthorized.
Forbidden означает «опознан, но не разрешено», Unauthorized — «не опознан».
Это два совершенно разных диагноза, и различать их надо: первый ведёт
к RBAC, второй — к сертификату.

Посмотреть все права субъекта одним списком:
kubectl auth can-i --list --as=k8suser


=========================================================================
9. Группы: выдавать права группе, а не человеку
=========================================================================

В сертификате мы указали O=developers — то есть группу. В прежней практике
это поле не использовалось, хотя это самый удобный механизм: выдать права
один раз группе, а не каждому пользователю по отдельности.

Работает точно так же, меняется только вид субъекта:

# === файл: rolebinding-group.yaml ===
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developers-binding
  namespace: default
subjects:
  - kind: Group
    name: developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: k8suser-reader
  apiGroup: rbac.authorization.k8s.io
# === конец файла ===

kubectl apply -f manifests/app_4_rbac/rolebinding-group.yaml

Проверим, что права действительно унаследованы от группы. Удаляем
персональную привязку и убеждаемся, что доступ сохранился:

kubectl delete rolebinding k8suser-binding
kubectl --context=k8suser-context auth can-i list pods
# yes — права пришли из группы developers

ПОЧЕМУ ЭТО ВАЖНЕЕ, ЧЕМ КАЖЕТСЯ: без групп приход нового разработчика
означает новую привязку, а уход — поиск и удаление всех его привязок
по кластеру. С группами достаточно выпустить сертификат с нужным O:
права появятся сами. А при увольнении нужно отозвать сертификат,
а не искать привязки.

СУЩЕСТВУЮТ ЛИ ГРУППЫ КАК ОБЪЕКТЫ: нет. Группа — это просто строка
в сертификате или токене. Kubernetes не проверяет, существует ли группа
developers, и не хранит её. Поэтому написать в привязке любое имя группы
можно, а получить его можно только через удостоверение.

ДОБАВЛЕНО, ПОЛЕЗНО ЗНАТЬ: есть встроенные группы, которые Kubernetes
использует сам:
  system:authenticated — все, кто успешно опознан;
  system:unauthenticated — те, кто не опознан;
  system:masters — группа администраторов, ей соответствует встроенный
    ClusterRoleBinding на cluster-admin. Если добавить в чей-то сертификат
    O=system:masters, этот человек получит неограниченный доступ.
    Это стоит помнить при аудите.


=========================================================================
10. ServiceAccount для CI/CD: самое опасное место
=========================================================================

ЗАЧЕМ: когда конвейер выкатывает приложение, он обращается к API-серверу.
Значит, ему нужны права — и здесь легко создать главную дыру в кластере.

СОБЛАЗН: выдать пайплайну готовую роль edit или сразу cluster-admin.
Тогда «всё просто работает». Но пайплайн — это код в репозитории, а доступ
к репозиторию есть у многих: разработчики, подрядчики, боты. Уязвимость
в зависимости сборки или подменённый скрипт в ветке получают доступ
ко всему кластеру, включая чтение всех секретов.

ПРАВИЛЬНЫЙ ПОДХОД: выдать ровно те права, которые нужны для выката.
Полный манифест — в manifests/app_4_rbac/ci-deployer.yaml, вот его суть:

# === файл: ci-deployer.yaml (фрагмент роли) ===
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: ci-deployer
  namespace: default
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
# === конец файла ===

РАЗБЕРЁМ, ЧТО ЗДЕСЬ ЕСТЬ И ЧЕГО НЕТ:

  есть deployments, services, configmaps — то, что выкатывается;
  есть pods только на чтение — чтобы работал kubectl rollout status;
  есть events на чтение — чтобы пайплайн мог сам напечатать причину
    неудачного выката;
  НЕТ secrets. Если пайплайну нужен секрет, он должен приходить
    из защищённых переменных CI или из внешнего хранилища (практика 7).
    Право читать секреты в namespace означает доступ ко всем паролям,
    включая чужие токены;
  НЕТ delete. Пайплайн, который умеет удалять, при ошибке в скрипте
    удалит прод. Если удаление действительно нужно — отдельная роль
    для отдельного окружения;
  НЕТ ClusterRole. Только Role, только свой namespace.

Проверяем, что получилось:
kubectl apply -f manifests/app_4_rbac/ci-deployer.yaml
kubectl auth can-i --list --as=system:serviceaccount:default:ci-deployer

Обратите внимание, что в списке нет secrets — и это то, чего мы добивались.

ОТДЕЛЬНО ПРО КАЖДОЕ ОКРУЖЕНИЕ: правильная схема — свой ServiceAccount
для каждого namespace. Пайплайн, выкатывающий на тест, не должен иметь
никакого доступа к проду. Это делается не ролями, а разными аккаунтами
с привязками в разных namespace.


=========================================================================
11. ClusterRole и агрегированные роли
=========================================================================

ЗАЧЕМ НУЖЕН CLUSTERROLE: Role действует в пределах namespace, но некоторые
объекты В ПРИНЦИПЕ не принадлежат namespace — nodes, persistentvolumes,
storageclasses, namespaces, сами объекты RBAC, описания CRD. Выдать права
на них через Role невозможно: Role просто не может на них ссылаться.

Типовая практика — чтение нод для приложения или мониторинга. Полный
манифест в manifests/app_4_rbac/clusterrole-node-reader.yaml, суть:

    apiVersion: rbac.authorization.k8s.io/v1
    kind: ClusterRole
    metadata:
      name: node-reader
    rules:
      - apiGroups: [""]
        resources: ["nodes"]
        verbs: ["get", "list", "watch"]

Обратите внимание: только чтение. Даже не list pods во всём кластере —
иначе приложение сможет перечислять чужие поды везде.

АГРЕГИРОВАННЫЕ РОЛИ — здесь стоит остановиться, потому что это неочевидная
и очень полезная возможность.

Посмотрите на встроенную роль edit:
kubectl get clusterrole edit -o yaml | head -20

У неё в spec ВООБЩЕ НЕТ списка rules. Вместо него — aggregationRule
с селектором по меткам, а правила подставляются из ролей, которые этим
меткам соответствуют. Именно так устроены встроенные view, edit и admin.

ЗАЧЕМ ЭТО НА ПРАКТИКЕ: у вас есть свой оператор со своими CRD. Ставя его,
вы добавляете новые типы объектов. И сразу вопрос: разработчикам нужна
роль edit, но она не знает про ваши типы, и они не смогут их редактировать.

Решение: чарт оператора вместе с CRD добавляет ещё одну ClusterRole
с меткой «включи меня в edit». Kubernetes сам подмешает её правила
к встроенной роли. Никто не правит системные роли, порядок установки
не важен.

Пример с двумя источниками и одной агрегированной ролью —
в manifests/app_4_rbac/clusterrole-aggregated.yaml. Контроллер RBAC
пересчитывает такие роли автоматически, обычно за секунды.


=========================================================================
12. Разбор проблем: почему прав нет
=========================================================================

Четыре ситуации, которые встречаются чаще всего. Все они объединены
одним: ошибок нигде не видно, доступ просто не работает.

ПРОБЛЕМА 1: FORBIDDEN ВМЕСТО UNAUTHORIZED

Сначала надо правильно поставить диагноз. Эти два ответа означают
совершенно разное:

  Unauthorized (401) — сертификат или токен не принят. Пользователь
    не опознан. Ищите проблему в аутентификации: не тот CA подписал
    сертификат, истёк срок, неверный kubeconfig.

  Forbidden (403) — пользователь опознан, но действие не разрешено.
    Ищите проблему в RBAC.

Во втором случае полезно узнать, кем вас видит кластер:
kubectl --context=k8suser-context auth whoami
# или для ServiceAccount:
kubectl auth whoami --as=system:serviceaccount:default:ci-deployer

Если имя не то, которое вы ожидали, — дальше искать бессмысленно.

ПРОБЛЕМА 2: ОПЕЧАТКА В ИМЕНИ

Здесь главная коварность RBAC: привязка ссылается на роль ПО ИМЕНИ
и НЕ ПРОВЕРЯЕТ, существует ли роль. Опечатка даёт рабочую привязку,
существующую роль — и ноль прав.

Проверяем связку вручную:
kubectl get rolebinding k8suser-binding -o yaml
kubectl get role k8suser-reader -n default

Имена должны совпадать буква в букву. Заодно проверьте namespace:
RoleBinding в одном namespace не видит Role из другого, и наоборот.

ПОЛЕЗНЫЙ ПРИЁМ — посмотреть, какие привязки реально дают права субъекту:
kubectl get rolebindings,clusterrolebindings -A -o json | \
  jq -r '.items[] | select(.subjects[]? | .name=="k8suser") | "\(.kind)/\(.metadata.namespace // "cluster")/\(.metadata.name) -> \(.roleRef.name)"'

ПРОБЛЕМА 3: ГРУППА НЕ СОВПАДАЕТ

Субъект kind: Group ищет группу в удостоверении. Для сертификата это поле O.
Если в сертификате O=devops, а в привязке name: developers — прав не будет,
и никакой ошибки тоже.

Проверить, какие группы видит кластер, можно так:
kubectl --context=k8suser-context auth whoami -o yaml

ПРОБЛЕМА 4: ПРАВА ЕСТЬ, НО НЕ В ТОМ NAMESPACE

Role и RoleBinding действуют строго в своём namespace. Пользователь с
правами в default не увидит ничего в kube-system — и это правильно.
Проверяйте, в каком namespace вы работаете:
kubectl config view --minify -o jsonpath='{.contexts[0].context.namespace}'


=========================================================================
13. Антипаттерны RBAC
=========================================================================

  * Выдавать cluster-admin, «чтобы не разбираться». Это отменяет весь
    смысл RBAC. В продакшене cluster-admin должен быть у считанных
    людей, а лучше — у одного автоматизированного процесса с аудитом.

  * Давать пайплайну право на secrets в namespace. Одно это право
    перевешивает всю остальную аккуратность: через него утекают пароли
    ко всем базам.

  * Использовать один ServiceAccount на все приложения в namespace.
    Тогда невозможно понять, кто что сделал, и невозможно ограничить
    права по-настоящему: у всех будет объединение прав.

  * Создавать пользователей через useradd и считать, что «добавил
    в кластер». В Kubernetes нет пользователей как объектов; нужен
    сертификат и привязка.

  * Выдавать права группе system:masters. Это неограниченный доступ,
    просто записанный иначе. Такие сертификаты не должны выпускаться
    никому, кроме администраторов кластера.

  * Забывать про automountServiceAccountToken. Токен монтируется
    по умолчанию даже туда, где не нужен.

  * Оставлять права на delete «на всякий случай». Право удалять,
    выданное заранее, рано или поздно сработает — при ошибке в скрипте
    или при неудачном рефакторинге.

  * Не проверять права после выдачи. Одна команда
    kubectl auth can-i --list --as=... показывает реальную картину
    за секунду. Пренебрегать ею — значит узнавать о проблеме
    из упавшего выката ночью.

  * Считать RBAC защитой секретов от администратора кластера.
    Администратор всё равно может выдать себе любые права. RBAC защищает
    от случайности и от рядовых участников, а не от того, кто управляет
    самим кластером.

УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

Манифесты:
kubectl delete -f manifests/app_4_rbac/clusterrole-aggregated.yaml --ignore-not-found
kubectl delete -f manifests/app_4_rbac/clusterrole-node-reader.yaml --ignore-not-found
kubectl delete -f manifests/app_4_rbac/ci-deployer.yaml --ignore-not-found
kubectl delete -f manifests/app_4_rbac/role.yaml --ignore-not-found
kubectl delete -f manifests/app_4_rbac/rolebinding.yaml --ignore-not-found
kubectl delete -f manifests/app_4_rbac/rolebinding-group.yaml --ignore-not-found

Созданные командами:
kubectl delete serviceaccount my-app-sa --ignore-not-found

Убираем пользователя из kubeconfig:
kubectl config delete-context k8suser-context
kubectl config delete-user k8suser

Удаляем ключи и сертификат:
rm -f k8suser.key k8suser.csr k8suser.crt

Удаляем пользователя ОС (он нужен был только как владелец файлов):
sudo userdel -r k8suser

УТОЧНЕНО: удаление пользователя ОС и удаление доступа в Kubernetes —
это независимые действия. Пользователь k8suser существует в кластере ровно
до тех пор, пока действителен подписанный сертификат: удаление записи
в ОС сам сертификат не отзывает. Отзыв сертификатов в kubeadm без
дополнительной настройки не поддерживается — именно поэтому срок действия
сертификата задают осознанно.

Проверяем, что чисто:
kubectl get role,rolebinding
kubectl get clusterrole | grep -E 'node-reader|monitoring-reader|ci-deployer'
