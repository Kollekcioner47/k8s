=========================================================================
ЗАЧЕМ НУЖЕН DEPLOYMENT, ЕСЛИ ЕСТЬ ПОД
=========================================================================

В практике 3 мы выяснили главное про под: он смертен и не воскресает.
Удалили под — он исчез. Упала нода — поды на ней не переехали. Для
учебных примеров это терпимо, для реальной работы — нет.

Deployment решает эту проблему и ещё две:

  * САМОВОССТАНОВЛЕНИЕ. Вы говорите «хочу 4 копии». Deployment следит
    за этим постоянно: под удалили — создаст новый, нода упала — поды
    переедут на другие.
  * ОБНОВЛЕНИЕ БЕЗ ПРОСТОЯ. Можно выпустить новую версию так, чтобы
    пользователи не заметили: новые поды поднимаются рядом со старыми,
    и только когда они готовы, старые убираются.
  * ОТКАТ. Если новая версия оказалась плохой, можно вернуться
    к предыдущей одной командой.

Ключевая идея, которую надо усвоить: Deployment НЕ управляет подами
напрямую. Он создаёт ReplicaSet, а уже ReplicaSet создаёт поды. Зачем
такой промежуточный уровень — разберём в части 2, там же выяснится, что
именно в нём и живёт вся механика обновлений.

И самое важное отличие от пода: Deployment описывает ЖЕЛАЕМОЕ состояние,
а не разовое действие. Вы пишете «хочу 4 копии этой версии», и Kubernetes
непрерывно приводит реальность к этому описанию. Из этого следуют две
практические вещи:
  * манифест можно применять повторно сколько угодно раз — объекты
    не задублируются;
  * удалить под руками бессмысленно: Deployment тут же создаст новый
    (мы это увидим в разделе 2).

ПОДЫ СОЗДАВАТЬ РУКАМИ БОЛЬШЕ НЕ БУДЕМ. Всё, что делали в практике 3
для понимания механики, в реальной работе делается через Deployment.

=========================================================================
1. Создаём Deployment командой
=========================================================================

Проверим список деплойментов:
kubectl get deploy

Пустой ответ — нормально, если вы только начали.

Создадим деплой:
kubectl create deployment first-deploy --image=YOUR_DOCKERHUB_LOGIN/k8sphp:version1

ЗАЧЕМ: та же логика, что и с kubectl run в практике 3. Это быстрый способ
поднять что-то для проверки. В реальной работе Deployment описывают
манифестом — по тем же причинам: десятки параметров в команду не влезут,
а манифест можно положить в git и отревьюить.


Снова проверим список деплоев:
kubectl get deploy

Обратите внимание на колонку READY: 1/1 означает «один под готов
из одного желаемого».

Проверим поды:
kubectl get pods

Посмотрим описание деплоя:
kubectl describe deployments first-deploy

ВАЖНОЕ ПРО РЕСУРСЫ: у деплоймента, созданного командой, нет ни requests,
ни limits. Такой под относится к классу BestEffort: при нехватке памяти
на ноде его вытеснят первым. Для учебного стенда сойдёт, для продакшена —
нет. Как правильно задавать ресурсы, разберём в разделе 7.


=========================================================================
2. Масштабирование
=========================================================================

Отмасштабируем деплой:
kubectl scale deployment first-deploy --replicas=4

ЗАЧЕМ: изменить количество копий можно в любой момент, без правки
манифеста. Но помните: если потом применить манифест, где указано другое
число реплик, оно вернётся к значению из файла. Манифест — источник истины.

Посмотрим реплики:
kubectl get rs

ЗАЧЕМ СМОТРЕТЬ ReplicaSet: это тот самый промежуточный уровень. Здесь
видно, что Deployment создал ReplicaSet со случайным суффиксом в имени
(например first-deploy-7d9f8c6b5d). Суффикс — это хеш от шаблона пода.
Именно поэтому при изменении шаблона появляется НОВЫЙ ReplicaSet, а старый
остаётся с нулём реплик — так и работает история версий для откатов.

Проверим масштабирование:
kubectl get pods

Теперь проверим самовосстановление на практике. Копируем имя одного
из подов и удаляем его:
kubectl delete pod ИМЯ_ПОДА
kubectl get pods

Удалённый под исчез, но появился новый — с другим именем. Обратите
внимание на AGE: новый под моложе остальных.

ПРО ЧЕГО ЭТО НЕ РАБОТАЕТ: если удалить сам Deployment, поды тоже исчезнут —
ReplicaSet и поды принадлежат ему, и удаляются каскадом. А вот если
удалить ReplicaSet напрямую, Deployment создаст новый. Иерархия владения
здесь строгая:

  Deployment  →  ReplicaSet  →  Pod

Проверить, кому принадлежит объект, можно так:
kubectl get pod ИМЯ_ПОДА -o jsonpath='{.metadata.ownerReferences[*].name}'


=========================================================================
3. Автомасштабирование
=========================================================================

ДОБАВЛЕНО, без этого шаг не работает. Для HorizontalPodAutoscaler нужны
две вещи, которых в курсе раньше не было:

  1) установленный metrics-server — источник метрик CPU и памяти;
  2) requests у контейнера — без них HPA не знает, от чего считать процент.

Устанавливаем metrics-server:
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

ОБЯЗАТЕЛЬНЫЙ ШАГ ДЛЯ УЧЕБНОГО КЛАСТЕРА: отключаем проверку сертификата
kubelet. Без этого metrics-server не заработает, и вот почему.

metrics-server обращается к kubelet на каждой ноде по HTTPS. kubelet
предъявляет сертификат, который в кластере, поднятом через kubeadm,
самоподписанный и не содержит IP-адреса ноды в поле SAN. metrics-server
такую проверку не проходит и падает с ошибкой:

    x509: cannot validate certificate for 192.168.250.2 because it
    doesn't contain any IP SANs

Снаружи это выглядит обманчиво: под metrics-server находится в Running,
в логах ошибки сыплются, а kubectl top отвечает «error: Metrics API not
available». Легко решить, что «metrics-server сломан», хотя дело
в сертификатах.

Добавляем флаг --kubelet-insecure-tls в аргументы deployment:
kubectl patch deployment metrics-server -n kube-system --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

Ждём, пока под пересоздастся:
kubectl rollout status deployment/metrics-server -n kube-system

ВАЖНО ПРО БЕЗОПАСНОСТЬ: флаг --kubelet-insecure-tls отключает проверку
сертификата kubelet, то есть metrics-server перестаёт убеждаться, что
отвечает именно тот kubelet, которому он доверяет. Для учебного стенда
это приемлемо. В продакшене так делать нельзя: там kubelet выдают
нормальные сертификаты с нужными SAN, и проверку отключать не требуется.

Проверяем, что он заработал (в ответе должны быть цифры, а не ошибка):
kubectl top nodes
kubectl top pods

Если всё равно ошибка — смотрим логи и убеждаемся, что флаг применился:
kubectl get deployment metrics-server -n kube-system -o yaml | grep -A5 args
kubectl logs -n kube-system deployment/metrics-server

Настройка автомасштабирования:
kubectl autoscale first-deploy --min=4 --max=6 --cpu-percent=80

ЗАЧЕМ: HPA следит за загрузкой и сам меняет число реплик. Логика простая:
если средняя загрузка CPU превышает 80% от requests, добавляем поды;
если падает — убираем, но не меньше min и не больше max.

Посмотрим horizontal-pod-autoscaling:
kubectl get hpa

ЧТО СМОТРЕТЬ В ВЫВОДЕ:
  NAME       REFERENCE                  TARGETS         MINPODS  MAXPODS  REPLICAS
  first-deploy  Deployment/first-deploy  0%/80%          4        6        4

Колонка TARGETS показывает текущий процент и цель. Если вы видите
<unknown>/80% — значит metrics-server не отдаёт метрики (см. выше) либо
у контейнера не заданы requests. Вторая причина встречается чаще, чем
кажется: без requests процент считать не от чего.

Про то, почему HPA «дёргается» и как это лечить, — раздел 13.

Посмотрим историю деплоя:
kubectl rollout history deployments/first-deploy

ПОЯСНЕНИЕ: колонка CHANGE-CAUSE почти наверняка будет пустой. Причина в том,
что флаг «kubectl apply --record» удалён начиная с Kubernetes 1.24, а именно
он заполнял эту колонку. Современный способ — добавлять аннотацию
kubernetes.io/change-cause вручную, например:
kubectl annotate deployment/first-deploy kubernetes.io/change-cause="update to version2"

Подробнее про историю ревизий — раздел 9.

Статус деплоя:
kubectl rollout status deployments/first-deploy

ЗАЧЕМ: команда показывает, завершилось ли обновление. Если оно зависло,
здесь будет видно: «Waiting for deployment ... rollout to finish».
При работе со скриптами и CI/CD эту команду используют, чтобы дождаться
окончания выката, а не гадать по таймауту.


=========================================================================
4. Обновление контейнера и откат
=========================================================================

Сначала посмотрим, какой контейнер используется:
kubectl describe deployment first-deploy

Ищем имя контейнера. ВАЖНО: у деплоймента, созданного командой
kubectl create deployment, имя контейнера совпадает с именем образа,
то есть будет k8sphp.

kubectl set image deployment/first-deploy k8sphp=YOUR_DOCKERHUB_LOGIN/k8sphp:version2

Проверим статус:
kubectl rollout status deployments/first-deploy
kubectl get pods

Что вы увидите: поды будут появляться постепенно, с разными именами.
Обратите внимание, что старые не исчезают мгновенно — это и есть
обновление по одному. Почему именно так и чем это регулируется — раздел 7.

Откат изменения:
kubectl rollout undo deployments/first-deploy

ЗАЧЕМ: откат — главная страховка при выкате. Он возвращает предыдущую
версию шаблона пода. При этом создаётся НОВАЯ ревизия — откат это тоже
изменение, и его тоже можно откатить.

Проверим, что вернулись:
kubectl rollout history deployments/first-deploy
kubectl describe deployment first-deploy | grep -i image


=========================================================================
5. Перезапуск деплоя
=========================================================================

kubectl rollout restart deployments/first-deploy

ЗАЧЕМ ЭТО НУЖНО, ЕСЛИ ОБРАЗ НЕ МЕНЯЛСЯ: перезапуск нужен, когда изменилось
не приложение, а его окружение. Например, вы поправили ConfigMap или Secret,
и поды должны перечитать настройки. Переменные окружения из ConfigMap
не обновляются на лету (мы это видели в практике 3), поэтому поды надо
пересоздать.

kubectl rollout restart делает это правильно: он проставляет аннотацию
с временной меткой в шаблон пода, из-за чего создаётся новый ReplicaSet,
и поды заменяются ПО ОДНОМУ — по правилам вашей стратегии обновления.
Это принципиально лучше, чем kubectl delete pods --all, который убьёт
все поды сразу и устроит простой.

6. Deployment через манифест
=========================================================================

# === файл: deploy-1-simple.yaml ===
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web-deploy
  labels:
    app: my-k8s-app
spec:
  replicas: 1
  selector:
    matchLabels:
      project: prod
  template:
    metadata:
      labels:
        project: prod
    spec:
      containers:
        - name: prod-web
          image: YOUR_DOCKERHUB_LOGIN/k8sphp:version1
          ports:
            - containerPort: 80
# === конец файла ===

РАЗБЕРЁМ ДВА ПОЛЯ, КОТОРЫХ НЕ БЫЛО У ПОДА:

  spec.replicas — сколько копий хотим. Если не указать, будет 1.
  spec.selector — по каким меткам Deployment считает поды «своими».
    ВНИМАНИЕ: в Deployment это поле ОБЯЗАТЕЛЬНОЕ, и после создания
    его изменить нельзя. В Pod его не было вовсе — под ни за кем не следит,
    а вот Deployment должен понимать, какие поды принадлежат ему.

Отсюда возникает связка, на которой спотыкаются все:
если selector.matchLabels не совпадает с template.metadata.labels,
манифест просто не применится. Под это правило важно не попадать случайно:
сравнивайте оба блока глазами, а лучше прогоняйте через
kubectl apply --dry-run=server (см. раздел 15).

Применяем:
kubectl apply -f manifests/04_deploy/deploy-1-simple.yaml
kubectl get deploy
kubectl get pods
kubectl get rs

Обратите внимание, что у реплики в имени есть хеш: 7d9f8c6b5d. Это хеш
шаблона пода. Поменяете шаблон — появится новый ReplicaSet с другим хешем.

Запустим форвардинг (подставьте имя любого из созданных подов):

# === файл: deploy-3-autoscaling.yaml ===
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web-deploy-autoscaling
  labels:
    app: my-k8s-app
    env: prod
    owner: Engineer
spec:
  replicas: 2
  selector:
    matchLabels:
      project: as
  template:
    metadata:
      labels:
        project: as
    spec:
      containers:
        - name: prod-web
          image: YOUR_DOCKERHUB_LOGIN/k8sphp:version2
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-autoscale
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-web-deploy-autoscaling
  minReplicas: 3
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
# === конец файла ===


kubectl apply -f manifests/04_deploy/deploy-3-autoscaling.yaml
kubectl get deploy
kubectl get pods
kubectl get hpa

ЗАМЕЧАНИЕ ПРО ДВА ПОКАЗАТЕЛЯ СРАЗУ: HPA может следить и за CPU, и за
памятью одновременно — как здесь. Но учтите, что масштабирование
по памяти работает плохо: приложения редко освобождают память обратно
(сборщик мусора, кэши), поэтому поды будут только добавляться. На практике
масштабируют почти всегда по CPU или по прикладным метрикам (запросы
в секунду, длина очереди).

=========================================================================
8. Как Deployment устроен внутри: ReplicaSet и метки
=========================================================================

Иерархия: Deployment → ReplicaSet → Pod.

Зачем понадобился ReplicaSet, если есть Deployment:

  * ReplicaSet умеет ровно одно — поддерживать нужное число одинаковых
    подов. Никакой истории версий и стратегий обновления у него нет;
  * Deployment — это надстройка, которая УПРАВЛЯЕТ ReplicaSet'ами.
    На каждую версию шаблона пода создаётся свой ReplicaSet.

Посмотрим на это своими руками:
kubectl get rs
kubectl get rs -o custom-columns='NAME:.metadata.name,DESIRED:.spec.replicas,READY:.status.readyReplicas,IMAGE:.spec.template.spec.containers[0].image'

Вы увидите несколько ReplicaSet с разными хешами в имени. У активного
число желаемых реплик больше нуля, у остальных — 0. Именно так хранится
история: старые ReplicaSet не удаляются, чтобы можно было откатиться.

Хеш в имени — это хеш шаблона пода (pod-template-hash). Он же добавляется
меткой ко всем подам. И вот здесь кроется важная деталь, на которой
ломаются самодельные селекторы:

kubectl get pod ИМЯ_ПОДА --show-labels

Вы увидите не только ваши метки, но и pod-template-hash=<хеш>. Deployment
добавляет эту метку автоматически, чтобы два ReplicaSet не «перетягивали»
поды друг у друга.

ЧТО ИЗ ЭТОГО СЛЕДУЕТ ПРАКТИЧЕСКИ: не пытайтесь делать Service, селектор
которого указывает на конкретный pod-template-hash. Такой Service умрёт
при первом же обновлении. Селектор Service должен опираться только
на ваши собственные метки — те, которые вы задаёте сами в template.

ПРОВЕРКА НА ПОНЯТИЕ: почему нельзя просто «удалить старый ReplicaSet,
чтобы не мешал»? Потому что вместе с ним исчезнет возможность
kubectl rollout undo на эту версию. Очисткой старых ReplicaSet занимается
сам Deployment — параметром revisionHistoryLimit (раздел 10).


=========================================================================
9. История ревизий и откаты
=========================================================================

Каждое изменение шаблона пода создаёт новую ревизию. Смотрим список:
kubectl rollout history deployment/first-deploy

ПРОБЛЕМА, С КОТОРОЙ СТОЛКНЁТСЯ КАЖДЫЙ: колонка CHANGE-CAUSE пустая.
Раньше для её заполнения использовали kubectl apply --record, но флаг
удалён в Kubernetes 1.24. Современный способ — аннотация:

kubectl annotate deployment/first-deploy kubernetes.io/change-cause="release 1.2.0: fix login bug" --overwrite

Делайте это в одном шаге с изменением — тогда история будет читаемой:
kubectl set image deployment/first-deploy k8sphp=YOUR_DOCKERHUB_LOGIN/k8sphp:version2
kubectl annotate deployment/first-deploy kubernetes.io/change-cause="release 1.2.0: update image to version2" --overwrite

Посмотреть подробности конкретной ревизии:
kubectl rollout history deployment/first-deploy --revision=2

ВЫБОРОЧНЫЙ ОТКАТ — то, чего не хватает в базовой версии:
kubectl rollout undo deployment/first-deploy --to-revision=1

ЗАЧЕМ: обычный rollout undo возвращает только предыдущую ревизию. А если
вы выпустили три версии подряд и проблема обнаружилась только сейчас,
нужно вернуться не на шаг назад, а на конкретную рабочую версию.

Проверить, что откат завершился:
kubectl rollout status deployment/first-deploy
kubectl rollout history deployment/first-deploy

ДОПОЛНИТЕЛЬНЫЙ ПРИЁМ — «сухой прогон» обновления. Если хочется узнать,
что изменится, ничего не применяя:
kubectl diff -f manifests/04_deploy/deploy-1-simple.yaml

Команда покажет построчную разницу между тем, что в кластере, и тем, что
в файле. Очень удобно перед применением в продакшене.


=========================================================================
10. Тонкие настройки: minReadySeconds, progressDeadlineSeconds,
    revisionHistoryLimit
=========================================================================

Эти три параметра не бросаются в глаза, но именно они отличают
аккуратный выкат от «вроде применилось, а что произошло — непонятно».

revisionHistoryLimit — сколько старых ReplicaSet хранить. По умолчанию 10.
Если поставить 0, откаты перестанут работать: откатываться будет некуда.

minReadySeconds — сколько под должен оставаться готовым, чтобы считаться
доступным. ЗАЧЕМ: readinessProbe может пройти один раз и сразу упасть
(приложение поднялось, отдало 200 и упало). minReadySeconds: 10 заставит
Deployment подождать десять секунд стабильной готовности, прежде чем
считать под удачным и переходить к следующему.

progressDeadlineSeconds — через сколько секунд без прогресса объявить
обновление неудачным. По умолчанию 600. ЗАЧЕМ: без этого зависший выкат
можно не заметить часами. С этим параметром kubectl rollout status
завершится ошибкой ProgressDeadlineExceeded, и вы узнаете о проблеме
сразу. Важно: превышение дедлайна НЕ откатывает обновление автоматически
и не останавливает его — Deployment продолжит пытаться. Он только
сообщает, что что-то идёт не так.

Полный манифест со всеми тремя параметрами — в файле
manifests/04_deploy/deploy-rolling-update.yaml.


=========================================================================
11. Стратегии обновления: RollingUpdate и Recreate
=========================================================================

# === файл: deploy-rolling-update.yaml (сокращённо, без комментариев) ===
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web-rolling
  labels:
    app: my-web
spec:
  replicas: 4
  revisionHistoryLimit: 5
  minReadySeconds: 5
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: my-web
      track: stable
  template:
    metadata:
      labels:
        app: my-web
        track: stable
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 2
            periodSeconds: 3
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
# === конец файла ===

Полная версия с комментариями лежит в
manifests/04_deploy/deploy-rolling-update.yaml — применяйте её.

ДВА ПАРАМЕТРА, КОТОРЫЕ ВСЁ ОПРЕДЕЛЯЮТ:

  maxSurge — на сколько подов МОЖНО превысить желаемое количество.
    maxSurge: 1 при replicas: 4 означает, что на пике будет 5 подов.
    Может задаваться числом или процентом (25%).

  maxUnavailable — сколько подов МОЖНО убрать, пока новые не готовы.
    Значение 0 — самое безопасное: ни один старый под не удалится,
    пока новый не станет готовым.

Комбинация maxSurge: 1 / maxUnavailable: 0 даёт обновление вообще
без потери ёмкости. Плата: обновление идёт медленнее и требует свободных
ресурсов на нодах — нужно место для пятого пода. Если ноды забиты под
завязку, поды некуда будет ставить, и выкат зависнет.

КОГДА ТАКАЯ КОМБИНАЦИЯ НЕ НУЖНА: если реплик много (10-20), потеря одного
пода незаметна, и можно позволить maxUnavailable: 1 — выкат пойдёт
быстрее. Значение по умолчанию, кстати, именно 25% — то есть «четверть
подов может быть недоступна во время обновления». Для двух-трёх реплик
это много, поэтому в продакшене параметры задают явно.

ГЛАВНОЕ УСЛОВИЕ, БЕЗ КОТОРОГО ВСЁ ЭТО НЕ РАБОТАЕТ: Deployment считает
новый под готовым по его readinessProbe. Если пробы НЕТ, Kubernetes
считает готовым под сразу после запуска процесса — трафик пойдёт
на приложение, которое ещё не поднялось. Внешне обновление «пройдёт
успешно», а пользователи поймают ошибки.

Отсюда правило: у любого приложения в Deployment должна быть
readinessProbe. Без неё стратегия обновления без простоя — фикция.
Сейчас убедимся в этом своими руками — см. раздел 14.

СТРАТЕГИЯ RECREATE: сначала удаляет ВСЕ старые поды, только потом создаёт
новые. Приложение полностью недоступно. Выглядит как шаг назад, но иногда
это единственный корректный вариант: если приложение не умеет работать
в двух версиях одновременно (например, новая версия поменяла формат
данных в базе, и старый код с ним не совместим). При RollingUpdate старые
и новые поды работают вместе и портят друг другу данные.

Выбор стратегии — это не «хорошо или плохо», а вопрос совместимости
версий. Манифест примера: manifests/04_deploy/deploy-recreate.yaml.


=========================================================================
12. Ручная канарейка: показать новую версию части пользователей
=========================================================================

ЗАЧЕМ: RollingUpdate обновляет ВСЕ поды. Но иногда новую версию хочется
сначала показать небольшой части трафика, убедиться, что она не падает,
и только потом раскатывать на всех.

СПОСОБ 1: ЗАМОРОЗИТЬ ВЫКАТ НА СЕРЕДИНЕ

kubectl set image deployment/first-deploy k8sphp=YOUR_DOCKERHUB_LOGIN/k8sphp:version2
kubectl rollout pause deployment/first-deploy

Выкат встанет на полпути: часть подов уже новая, часть старая. Можно
посмотреть, как ведёт себя новая версия, и либо продолжить, либо откатить:

kubectl get pods
# ... проверяем работу ...
kubectl rollout resume deployment/first-deploy     # продолжить
# или
kubectl rollout undo deployment/first-deploy       # откатить

Приём простой, но пропорция управляется грубо: она зависит от того,
на каком шаге вы нажали pause.

СПОСОБ 2: ДВА DEPLOYMENT НА ОДИН SERVICE

Аккуратный вариант — держать два Deployment одновременно и дать им делить
трафик одного Service. Работает за счёт меток:
  * общая метка (app: my-web-canary) — её выбирает Service, поэтому
    в балансировку попадают поды ОБЕИХ версий;
  * различающая метка (track: stable / track: canary) — по ней видно,
    кто есть кто.

Пропорция задаётся ЧИСЛОМ РЕПЛИК: 4 старых и 1 новая дадут примерно
20% трафика на новую версию.

Полный манифест — manifests/04_deploy/deploy-canary.yaml. В нём
использован hashicorp/http-echo: он возвращает заданный текст, поэтому
сразу видно, какая версия ответила. Для учебной демонстрации это
нагляднее одинаковых страниц nginx.

Применяем и смотрим, кто отвечает:
kubectl apply -f manifests/04_deploy/deploy-canary.yaml
kubectl get pods -l app=my-web-canary --show-labels

Запускаем проверку. Обратите внимание: снаружи пода к ClusterIP не
достучаться (см. практику 5), поэтому проверяем через port-forward:
kubectl port-forward svc/my-web-canary-service 8080:80

И во втором терминале несколько раз подряд:
for i in $(seq 1 10); do curl -s http://127.0.0.1:8080; echo; done

Вы увидите, что примерно каждый пятый ответ — CANARY version 2. Соотношение
задаётся количеством реплик.

ОГРАНИЧЕНИЕ ПРИЁМА: пропорция получается грубой, управлять ей точно
(например, 1% трафика) без service mesh или ingress-аннотаций нельзя.
Зато не нужно ничего дополнительно устанавливать — и это честный ответ
на вопрос «а как сделать канарейку без Istio».

КОГДА КАНАРЕЙКА ЗАВЕРШИЛАСЬ УСПЕШНО: увеличиваем replicas у canary
и уменьшаем у stable, затем удаляем stable-деплоймент:
kubectl scale deployment my-web-canary --replicas=4
kubectl scale deployment my-web-stable --replicas=1
# ... убедились ...
kubectl scale deployment my-web-stable --replicas=0
kubectl delete deployment my-web-stable

13. HPA с настройкой поведения: почему он «дёргается»
=========================================================================

ЗАЧЕМ: обычный HPA реагирует на каждое колебание метрики. Нагрузка
подскочила на минуту — HPA поднял десяток подов, нагрузка упала — снова
убрал. Каждый запуск пода это время и ресурсы, а для приложений
с прогревом кэша — ещё и деградация.

Блок behavior задаёт правила: насколько резко масштабироваться и сколько
времени ждать перед решением.

# === файл: hpa-behavior.yaml ===
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-web-rolling
  minReplicas: 2
  maxReplicas: 8
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 30
        - type: Pods
          value: 4
          periodSeconds: 30
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 25
          periodSeconds: 60
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
# === конец файла ===

ЛОГИКА, КОТОРУЮ СТОИТ ЗАПОМНИТЬ:

  scaleUp — реакция быстрая. stabilizationWindowSeconds: 0 и разрешение
    удвоить число подов за 30 секунд. Лучше поднять лишний под, чем
    получить отказ в обслуживании.

  scaleDown — наоборот, спешить некуда. stabilizationWindowSeconds: 300
    означает: HPA сначала 5 минут смотрит на метрики и берёт САМОЕ ВЫСОКОЕ
    значение за это окно. Если нагрузка была высокой минуту назад, снижать
    количество подов рано.

Асимметрия здесь намеренная и хорошо описывает правильный подход:
подниматься быстро, опускаться осторожно.

Про selectPolicy: Max — когда задано несколько политик, нужно указать,
какую выбрать при расхождении. Max означает «применяем ту, что разрешает
больше изменений», Min — «ту, что разрешает меньше».

Применяем и наблюдаем:
kubectl apply -f manifests/04_deploy/deploy-rolling-update.yaml
kubectl apply -f manifests/04_deploy/hpa-behavior.yaml
kubectl get hpa -w

Посмотреть, какое поведение реально применилось:
kubectl describe hpa my-web-hpa

14. Пропал простой? Разбираем зависший выкат
=========================================================================

Это самый частый вопрос при первом знакомстве с Deployment: «применил
манифест, а ничего не меняется». Разберём это своими руками.

Сначала поднимем нормальный деплоймент:
kubectl apply -f manifests/04_deploy/deploy-rolling-update.yaml
kubectl rollout status deployment/my-web-rolling

Теперь сломаем readinessProbe — сделаем так, чтобы новые поды НИКОГДА
не стали готовыми. Именно так выглядит реальная ситуация «приложение
поднялось, но не отвечает на /healthz»:

kubectl patch deployment my-web-rolling --type=json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/not-found"}]'

Смотрим за выкатом:
kubectl rollout status deployment/my-web-rolling

Команда будет ждать и в итоге выведет примерно такое:
  Waiting for deployment "my-web-rolling" rollout to finish:
  1 out of 4 new replicas have been updated...

А теперь самое интересное:
kubectl get pods

Вы увидите 5 подов (4 старых + 1 новый, потому что maxSurge: 1):
  * старые — Running, READY 1/1;
  * новый — Running, но READY 0/1.

КЛЮЧЕВОЙ МОМЕНТ, КОТОРЫЙ НАДО ПОНЯТЬ: выкат ЗАВИС, но приложение
не упало. Все старые поды продолжают работать и обслуживать трафик —
именно потому, что мы поставили maxUnavailable: 0. Новый под не получает
трафик, потому что не проходит readiness. Никакого простоя нет.

Если бы maxUnavailable был больше нуля, Deployment уже удалил бы часть
старых подов, и ёмкость приложения упала бы. Вот наглядная разница между
аккуратными настройками и настройками по умолчанию.

Разбираемся, почему новый под не готов:
kubectl describe pod ИМЯ_НОВОГО_ПОДА
# в разделе Events будет: Readiness probe failed: HTTP probe failed
# with statuscode: 404

kubectl logs ИМЯ_НОВОГО_ПОДА
# в логах приложения всё чисто — оно живо, просто проба бьёт не туда

ВОТ ГЛАВНЫЙ ВЫВОД ЭТОГО РАЗДЕЛА: если под в состоянии Running, а READY
0/1 — проблема НЕ в приложении, а в пробе. Логи в этом случае могут быть
абсолютно пустыми и ничего не объяснить. Всегда проверяйте Events.

Откатываем и убеждаемся, что всё вернулось:
kubectl rollout undo deployment/my-web-rolling
kubectl rollout status deployment/my-web-rolling
kubectl get pods

АЛГОРИТМ РАЗБОРА ЗАВИСШЕГО ВЫКАТА — запомните эту последовательность:

  1. kubectl get deploy
     Смотрим колонки READY и UP-TO-DATE. Расхождение уже говорит о зависании.

  2. kubectl rollout status deployment/DEPLOY_NAME
     Показывает, на каком именно шаге встало.

  3. kubectl get pods
     Ищем поды с READY 0/1. Это «виновники».

  4. kubectl describe pod ВИНОВНИК
     Раздел Events. Здесь написана причина: не проходит проба, не
     скачивается образ, не хватает ресурсов.

  5. kubectl get rs
     Если новых подов нет вообще — проверьте, создался ли новый ReplicaSet.
     Если нет, значит Deployment не понял, что шаблон изменился
     (например, вы поменяли поле, которое на самом деле не изменилось).

  6. kubectl describe deployment ИМЯ
     В самом низу, в Conditions, будет Progressing со статусом False
     и причиной. Например ProgressDeadlineExceeded или ReplicaFailure.

ЧАСТЫЕ ПРИЧИНЫ ЗАВИСШЕГО ВЫКАТА:
  * readinessProbe бьёт по неверному пути или порту — самый частый случай;
  * образ не скачивается (опечатка в теге, приватный реестр без секрета);
  * не хватает ресурсов на нодах: новые поды некуда поставить,
    они в Pending;
  * приложение стартует дольше, чем позволяет прогресс-дедлайн;
  * PVC не может связаться с PV — поды висят в ContainerCreating.


=========================================================================
15. PDB: защита от выключения нод
=========================================================================

ЗАЧЕМ: RollingUpdate защищает приложение при обновлении самого Deployment.
Но есть ещё один источник простоев, о котором новички не думают, — плановые
работы на нодах: обновление кластера, замена железа, масштабирование
down, drain ноды.

Есть два вида вытеснения подов, и их важно различать:

  НЕДОБРОВОЛЬНОЕ — нода упала, закончилась память, ядро убило процесс.
    Повлиять на это нельзя, PDB здесь не поможет.

  ДОБРОВОЛЬНОЕ — нода выводится на обслуживание (kubectl drain),
    идёт обновление кластера. Здесь Kubernetes СПРАШИВАЕТ разрешения,
    и именно тут работает PodDisruptionBudget.

Без PDB команда kubectl drain спокойно выселит с ноды ВСЕ поды сразу.
Если это была единственная нода с вашим приложением — будет простой.

# === файл: pdb.yaml ===
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-web-pdb
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: my-web
      track: stable
# === конец файла ===

minAvailable считается от желаемого числа реплик: при replicas: 4
и minAvailable: 3 одновременно можно вывести из строя один под.

Альтернатива — maxUnavailable: 1. Разница проявляется при масштабировании:
minAvailable при уменьшении replicas может заблокировать drain целиком
(например, если реплик стало 3, а minAvailable остался 3 — выселять
нельзя никого), maxUnavailable ведёт себя предсказуемее. Для большинства
случаев рекомендуется maxUnavailable.

ВАЖНО: PDB не влияет на RollingUpdate! Он защищает только от добровольных
нарушений, а не от действий самого Deployment. Это частое заблуждение:
люди ставят PDB и думают, что обновления стали безопаснее. Нет — за
безопасность обновления отвечают maxSurge и maxUnavailable.

Применяем и проверяем:
kubectl apply -f manifests/04_deploy/deploy-rolling-update.yaml
kubectl apply -f manifests/04_deploy/pdb.yaml
kubectl get pdb

Обратите внимание на колонку ALLOWED DISRUPTIONS — сколько подов сейчас
можно вывести из строя, не нарушив бюджет.

Посмотреть, как это работает, можно на учебном кластере:
kubectl drain ИМЯ_НОДЫ --ignore-daemonsets --delete-emptydir-data --dry-run=client

Ключ --dry-run=client покажет, что произойдёт, ничего не делая. Уберите
его, когда будете готовы (и не делайте этого, если на ноде есть что-то
важное).


=========================================================================
16. Чек-лист: каким должен быть Deployment в продакшене
=========================================================================

Собрали всё из части 2 в один список. По нему удобно проверять чужой
манифест и свой собственный.

ОБЯЗАТЕЛЬНО:
  [ ] readinessProbe есть. Без неё обновление без простоя невозможно:
      трафик пойдёт на неподнявшееся приложение.
  [ ] livenessProbe есть, но осознанно. Для медленно стартующих
      приложений добавлена startupProbe, иначе liveness будет убивать
      поды на старте.
  [ ] requests заданы по CPU и памяти. Без них под не учитывается
      планировщиком, HPA не работает, а класс QoS — BestEffort,
      то есть поды вытеснят первыми.
  [ ] limits заданы. Лимит памяти защищает соседей от утечки в вашем
      приложении.
  [ ] Тег образа конкретный (version1, а не latest). С latest невозможно
      понять, какая версия работает, и невозможно осмысленно откатиться.
  [ ] maxUnavailable и maxSurge заданы явно. Значение по умолчанию 25%
      для двух-трёх реплик означает заметную потерю ёмкости.
  [ ] replicas не 1. Одна реплика — это гарантированный простой при
      обновлении и при падении ноды.
  [ ] revisionHistoryLimit задан. Значение по умолчанию 10 нормально,
      но 0 отключает откаты.

ХОРОШО БЫ ИМЕТЬ:
  [ ] securityContext: runAsNonRoot, allowPrivilegeEscalation: false,
      capabilities.drop: [ALL] — см. практику 3.
  [ ] PodDisruptionBudget, если приложение критично и ноды когда-нибудь
      будут выводить на обслуживание.
  [ ] minReadySeconds, если приложение может «подняться и сразу упасть».
  [ ] progressDeadlineSeconds, чтобы зависший выкат было видно.
  [ ] Один и тот же образ проверен на тестовом стенде до продакшена.
      Логика простая: сначала staging, потом production.

АНТИПАТТЕРНЫ, КОТОРЫЕ ВСТРЕЧАЮТСЯ ЧАЩЕ ВСЕГО:
  * kubectl delete pods --all вместо kubectl rollout restart;
  * отсутствие проб с надеждой на «и так работает»;
  * latest в теге образа;
  * одинаковые requests и limits «на всякий случай» без понимания
      реального потребления;
  * HPA без requests — он просто не работает, но об этом легко не узнать;
  * правка объектов «руками» через kubectl edit без изменения манифеста
      в git. Следующее применение манифеста всё вернёт назад,
      и это будет неприятным сюрпризом.
